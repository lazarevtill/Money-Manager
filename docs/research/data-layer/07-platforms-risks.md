## Platforms, risks and open questions

The two platforms are not two implementations of one design. They differ in what can be captured at
all, in whether background work is a guarantee or a hope, in where the database is allowed to live,
and in what the OS does with the file behind your back. Everything above this section — the schema
in §3, the pipeline in §4 — is deliberately written once and shared; this section is the accounting
of what that costs and where the shared abstraction is a polite fiction.

Provenance is marked on every non-obvious claim:

| Mark | Meaning |
| --- | --- |
| **[V]** | Verified against a primary source during the research pass — AOSP source, Apple documentation, a package tarball, the SIX/ISO list, or Play policy text |
| **[R]** | Reported by a credible secondary source (practitioner writeup, forum thread with reproduction), not confirmed against a primary |
| **[I]** | Inference or design judgement |
| **[NEW]** | Found while writing this section, by reading §3 or by direct test — **has not been through any other source check** |

### 7.1 iOS vs Android — where the platforms diverge

#### 7.1.1 Capture

| Dimension | Android | iOS |
| --- | --- | --- |
| Passive capture | `NotificationListenerService` (`BIND_NOTIFICATION_LISTENER_SERVICE`); `READ_SMS` added later **[V]** | **None. Zero.** No SMS read, no reading other apps' notifications |
| Near-passive | — | Wallet/Transaction Shortcuts automation on an Apple Pay **NFC tap** → your App Intent, handing over Merchant, Amount, Card, Date **[R]** |
| What near-passive misses | — | In-app and web Apple Pay, physical-card purchases, cash, transfers. Reported to time out with some card providers and to deliver empty merchant / zero amount on iOS 18 **[R]** |
| User-initiated | Share sheet, camera, voice, manual, SAF file import | Share Sheet extension, Shortcuts/App Intents, screenshot OCR, camera, voice, manual, document picker |
| Retroactive backfill | `content://sms/inbox` is a queryable historical store — months recoverable on first grant **[V]** | **Nothing.** No notification equivalent exists; statement import is the only route to history |
| Redaction | Android 15+ redacts "sensitive" notifications for third-party listeners: `EXTRA_TITLE` → the posting app's label, `EXTRA_TEXT` → "Sensitive notification content hidden", `EXTRA_TEXT_LINES` and `EXTRA_SUB_TEXT` removed **[V]**. SMS text is never redacted **[V]** | n/a |
| Redaction detection | No public API — `Ranking` has no `hasSensitiveContent()` through API 36 **[V]**. **Detection is the D69 differential test on the app's own `skeleton` fingerprint history, set at drain time; `getApplicationLabel()` equality is a corroborating signal only, inside a `try/catch` that distinguishes "label unavailable" from "label differs".** Recorded as `raw_captures.redaction_suspected` | n/a |
| Package visibility | Under Android 11+ filtering it is **not established** that a bound `NotificationListenerService` can resolve the packages posting to it; `getApplicationInfo()` may throw `NameNotFoundException`. `QUERY_ALL_PACKAGES` is not an escape — Play-restricted, and budgeting is not on the permitted-use list **[I, spike B13]**. This is why label equality cannot be the primary redaction test, and it also decides whether the sender-picker UI can enumerate installed bank apps at all | n/a |
| Custom-view blind spot | Apps targeting API 31+ **cannot** post fully custom notifications; the system applies a `DecoratedCustomViewStyle`-equivalent template **[V]**, so the unreadable set is small. Do not scrape `RemoteViews` by reflection **[R]** | n/a |
| Group summaries and in-place updates | **Both break dedupe gate G5's premise.** An app posting >1 notification in a group also posts a group summary, which under `InboxStyle` repeats the child lines *including amounts* with a different `getKey()` and `postTime`; banks also update a notification in place (pending → confirmed) re-posting the same `getKey()` with different text. Producer drops `FLAG_GROUP_SUMMARY` as `ignored`/`group_summary`; identical `source_ref` is a supersede, not a second authorization (**D128**) | n/a — a Wallet tap posts nothing |
| Gap visibility | **Foreground reconciliation is primary** (grant check → hibernation check → heartbeat and per-sender inter-arrival staleness); the WorkManager probe is an accelerator whose period is unbounded (§7.1.2). `capture_gaps` causes: `binding_died`, `oem_killed`, `permission_revoked`, `boot_before_unlock`, `probe_failed`, `app_updated`, `user_disabled`, `spool_full`, `spool_key_lost`, `hibernated`, `force_stopped`, `mirror_unavailable`, `app_replaced` (**D71**) | Almost nothing to probe. Practical signal is `last_wallet_capture_at` staleness and the user noticing |
| Duplicate pressure | **High** — the same purchase arrives as a bank notification, as the messaging app relaying a bank SMS (`android_notification_sms`), and as the SMS provider row; plus group summaries and in-place updates above | **Low** — a Wallet tap plus a receipt shared hours later |
| Allowlist reachability | The allowlist the producer enforces is **not** `capture_senders` — Kotlin cannot read SQLCipher (§7.1.3). It is the versioned `capture/senders.v1.json` mirror (**D127**), fail-closed, with a `nomirror` marker the drain converts into a retroactive gap | n/a |
| Policy gate | Play SMS/Call Log declaration; the "SMS-based money management … apps that track and manage budget" carve-out is still present as of the July 2026 policy round **[V]**. No declaration form exists for notification access **[V]** | App Review only; no equivalent permission declaration |

`source_channel` in `raw_captures` is the single column carrying this divergence:
`android_notification`, `android_notification_sms`, `android_sms` on one side;
`ios_share`, `ios_shortcut`, `ios_wallet_intent` on the other; `screenshot_ocr`, `camera_receipt`,
`voice`, `manual_text`, `file_import`, `statement_import` shared.

#### 7.1.2 Background execution

| Dimension | Android | iOS |
| --- | --- | --- |
| Is capture itself background work? | No. The system binds the listener with `BIND_AUTO_CREATE \| BIND_FOREGROUND_SERVICE \| BIND_ALLOW_WHITELIST_MANAGEMENT` **[V]**, so the process already has foreground-service `oom_adj` | There is no passive capture to schedule |
| Foreground service needed? | **No** — and declaring one would buy a Play Console review, the Android 15 `dataSync` 6h/24h cap with ANR-on-timeout, and a persistent notification, for nothing **[V]** | n/a |
| Doze / App Standby | Does **not** stop binder callbacks to a bound listener — capture is Doze-insensitive. Doze defers the *deferred* work: extraction, the probe, any user-owned-endpoint sync **[V]** | Low Power Mode, thermal pressure and usage patterns all suppress background tasks **[R]** |
| Deferred-work API | WorkManager, expedited available. Android 16 ties job quota to the App Standby bucket and charges jobs running concurrently with an FGS against quota **[V]** | `BGTaskScheduler`: identifiers must be in `BGTaskSchedulerPermittedIdentifiers` **and** registered before `didFinishLaunching` returns; `earliestBeginDate` is a lower bound, not a schedule; one pending request per identifier **[V]** |
| Scheduling guarantee | Throttled and OEM-killed, but real — **with one exception that voids it entirely: force-stop.** OEM battery managers, App Hibernation and the user all kill by force-stop, which puts the package in the *stopped* state and **cancels its scheduled jobs**; WorkManager does not reschedule until something in the app runs again. A watchdog implemented purely as periodic work therefore dies with the thing it watches **[I, field knowledge — verify on the B3 device mix]** | **None whatsoever.** Force-quit from the app switcher stops background execution entirely until a manual relaunch **[R]** |
| Detection latency you may promise from deferred work | **None.** On top of force-stop, Android 16's per-bucket quota means a weekly-use budgeting app sits in RARE/RESTRICTED where the probe runs at most daily even when nothing is killing it. **No gap-detection SLA may be derived from the probe**; the promise is foreground reconciliation (D68) | n/a |
| What deferred work can and cannot write | A WorkManager `Worker` is a Kotlin class, so it **cannot** advance `capture_health` or open a `capture_gaps` row — same op-sqlite limitation as the listener (§7.1.3). It appends to `capture/heartbeat.log`; the drain folds it in (**D127**) | n/a |
| User-initiated long work | Expedited WorkManager | `BGContinuedProcessingTask` (iOS 26) — starts immediately from an explicit user action, continues after backgrounding, system-rendered progress with a cancel affordance, deprioritized if it reports little progress **[R]** |
| GPU in background | Available (no FGS involved) | **Unavailable on every iPhone.** `BGTaskScheduler.supportedResources.contains(.gpu)` reported `false` on iPhone 15 Pro and 16 Pro under iOS 26; iPad M3+ only **[R]** |
| Consequence for extraction | Can run on GPU in a deferred job | Background extraction is CPU-only. **Foreground drain is the primary path and correctness never depends on background** |
| Battery-exemption prompt | Do **not** hold `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` — Play prohibits direct exemption requests outside a list that does not clearly cover budgeting **[V]**. Use `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS` (no permission) from a troubleshooting screen only **[V]** | n/a |

Both platforms therefore land on the same product sentence, for different reasons: **the queue drains
on next foreground launch, and the UI shows how many items are waiting.** Background scheduling is an
accelerator that makes that number smaller, never a promise.

#### 7.1.3 Storage location and process boundaries

| Dimension | Android | iOS |
| --- | --- | --- |
| Capture process | The app's own process (a bound service in the app manifest) **[V]** | A **separate** extension process, killed at ~120 MB resident; `com.apple.developer.kernel.increased-memory-limit` does **not** raise it **[R]** |
| Can the capture path write the DB directly? | **No** — op-sqlite's entire Android Kotlin surface is 157 lines exposing only `install()`, `getDylibPath()`, `moveAssetsDatabase()`; everything else is a JSI `HostObject` reachable only from a JS runtime **[V]** | **No** — SQLCipher + WAL inside an App Group container is a deterministic `0xdead10cc` termination on **every** backgrounding, on all iOS versions and devices **[V]** |
| Why the answer is "no" differs | A process-model non-issue blocked by a **binding** limitation | A binding non-issue blocked by a **process-model** limitation |
| Resolution | Identical: producers write a sealed, atomically-renamed spool file; the main app drains it into `raw_captures` | Identical |
| **Everything else the native side needs from SQLite** | **The D127 mirror contract, and nothing else.** The allowlist, the liveness heartbeat, and the redaction fingerprint history are all SQLite-resident and all needed natively; without one named, versioned mechanism each is rediscovered per feature and each fails toward *silence*. JS writes `capture/senders.v1.json` (write-tmp-then-rename, monotonic `mirror_version`); Kotlin appends `capture/heartbeat.log`; the producer fails **closed** and drops a `capture/nomirror.<epoch_ms>` marker the drain turns into a `capture_gaps` row | Same file-based contract, App Group container. The iOS producers need far less of it — there is no allowlist to consult for a Share Sheet invocation |
| Spool location | **`context.getFilesDir()/spool/` — credential-protected.** Do **not** call `createDeviceProtectedStorageContext()`: it extends no capability (nothing can post pre-unlock, and the unsealing key is DEK-derived and therefore CE-gated regardless), it downgrades the protection class on the most sensitive bytes in the app, and device-protected storage is backup domain `device_file`, so a `<exclude domain="file" path="spool/">` silently matches nothing. §3.10 and D60's parenthetical are corrected to match (**N5**) | App Group container, `staging/{tmp,inbox}` — there is no `processed/`; the drain **deletes** the record after its transaction commits (**D57**) |
| Spool commit marker and durability | Write `.part` → `fd.sync()` → atomic `rename()` into `inbox/` → `fsync()` the `inbox/` directory fd. Media first, **manifest last**. `rename()` atomicity covers the directory entry, not the data: f2fs (the default on most of the B3 device mix) has no ext4-style replace-via-rename writeback heuristic, so without the syncs a power loss commits a correctly-named, truncated manifest **[I]** | Same sequence. An orphan media file with no manifest is swept after 24 h |
| Spool at-rest protection | Sealed box under a key **derived from the DEK** (`crypto_kdf_derive_from_key(DEK, "mmspool")`), not a second Keystore-only secret — see R33. §4.4.1's "the private key lives in the keystore" was also not implementable as written: `crypto_box_seal_open()` needs the raw X25519 scalar and a Keystore key is non-extractable | `NSFileProtectionCompleteUntilFirstUserAuthentication` + the same DEK-derived sealed box |
| Threading in the capture callback | `onNotificationPosted` and `onListenerConnected` are dispatched on the service's **main Looper** — the thread RN renders on. The callback thread does exactly one thing: copy every extra out of the parcel-backed `Bundle` into an immutable data class. Hashing, sealing and file I/O run on a single dedicated `HandlerThread`, serialized so spool order still matches arrival order; `onListenerConnected`'s reconciliation batch is capped (**D57a**) | The extension has its own process and its own 120 MB ceiling; the constraint is memory, not thread affinity |
| Database location | App internal storage | The app's **own container**, never the App Group |
| Media | Filesystem under a media root, `media_assets` rows hold `rel_path` (relative — iOS rewrites the container UUID on restore) | Same |
| Extension memory rule | n/a | Copy bytes with `loadFileRepresentation` + `copyItem`. **Never** `loadObject(ofClass: UIImage.self)` and never resize — decoding a 12 MP photo blows the budget. Downscale in the main app at drain time **[R]** |

The 120 MB ceiling settles the on-device-model question for iOS ingestion without argument: Gemma 4
E2B is ~0.84 GB, roughly 7× over, before the JPEG or any runtime. **The Share Extension stages; it
never parses.**

#### 7.1.4 Encryption, keys and platform backup

| Dimension | Android | iOS |
| --- | --- | --- |
| Platform encryption at rest | File-Based Encryption. Credential-encrypted storage unlocks at the **first** unlock after boot and stays unlocked until reboot — locking the screen again does not re-lock it **[V]** | Data Protection; app container default is `NSFileProtectionCompleteUntilFirstUserAuthentication` |
| DB encryption | SQLCipher via op-sqlite (`"op-sqlite": { "sqlcipher": true }`), keyed by `sqlite3_key_v2()` before any statement runs **[V]** | Same |
| Key form | A **raw 32-byte DEK** passed as the exact 67-character string `x'<64 hex>'`, which bypasses 256,000-iteration PBKDF2-HMAC-SHA512 and makes cold open a memcpy **[V]** | Same |
| Key wrap A (silent open) | Keystore `AES/GCM/NoPadding`, **`setUserAuthenticationRequired(false)` and `setUnlockedDeviceRequired(false)`** — both default to false, and setting either true breaks the 3 a.m. bank-alert write **[V]** | Keychain, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` |
| Key wrap B (recovery) | **§6.1 is the single normative spec** (D4): Argon2id over an app-generated **15-word BIP39 phrase** → XChaCha20-Poly1305 over the DEK → `<appdir>/keys/recovery.wrap`. §2.7's PBKDF2 + AES-GCM + 32-char base32 variant is struck. **Not optional** — see R1 | Same |
| Wrap-B file format | **Self-describing and versioned** (D4a): `[magic][version][kdf_id][m_kib][t][p][salt:16][nonce:24][AEAD(DEK)][tag]`. Nothing outside the file may be needed to unwrap it — both paths that need Wrap B (a Keystore invalidation, a D2D restore) have neither an openable database nor a manifest. `meta.recovery_salt_hex` and the manifest `kdf` block are convenience copies. Gate G-16 | Same |
| Secret inventory | **Every** Keychain/Keystore item is enumerated once (D119) and carries the same class: the Wrap-A wrapper, `backup_kek`, the WebDAV credential. There is deliberately no separate spool secret — it is DEK-derived (D57a). Gate G-10 iterates the enumeration | Same, plus `kSecAttrSynchronizable = false` on every item. `expo-secure-store` defaults to `WHEN_UNLOCKED`, which is neither `AfterFirstUnlock` nor `ThisDeviceOnly` — a `backup_kek` written with no options is iCloud-Keychain-eligible **[V]** |
| Why wrap B is mandatory | Keystore keys are hardware-bound and non-extractable **[V]** | iCloud Backup's keychain copy is encrypted under a Secure Enclave UID key and "can be restored only to the same device"; `…ThisDeviceOnly` items never migrate **[V]** |
| File protection ceiling | n/a | Do **not** raise the DB or its `-wal`/`-shm` siblings to `NSFileProtectionComplete` — writes would fail whenever the screen is locked |
| Platform backup default | `android:allowBackup` defaults **true** and includes `getDatabasePath()`; 25 MB/app quota, then `onQuotaExceeded()` and no backup at all **[V]** | iCloud Backup includes `Library/` by default; only `Caches/` and `tmp/` are excluded **[V]** |
| Backup configuration | Keep `allowBackup="true"`, and make `<cloud-backup>` **deny-all by construction** — a root `<exclude>` per domain (`file`, `database`, `sharedpref`, `external`, `root`, and the `device_*` variants) — with `<device-transfer>` include-only: `database .`, `file media/`, `file keys/`, `file capture/`. One exported path constant, asserted by **string equality** in G-7. Parallel `fullBackupContent` for API ≤30 (D9, D9a) | `NSURLIsExcludedFromBackupKey = true` on the **directories** `db/`, `media/`, `keys/`, `export/`, `snapshots/` and `restore/` — not on files, since `-wal`/`-shm` are created after the fact |
| Cross-device restore | `<device-transfer>` D2D **plus** the recovery phrase (Keystore material does not transfer). This entire position rests on `keys/recovery.wrap` actually arriving — spike **B11** | The `.mmbak` export plus the recovery phrase. Nothing else |
| Backup primitive | `ATTACH '<path>' AS bk KEY "x'…'"; SELECT sqlcipher_export('bk');` — one consistent encrypted file under a **different** key, with no plaintext intermediate **[V]** | Same |

**Four conflicts, resolved here so a reader who saw the raw agent output — or an earlier draft of
this document — does not think this section is wrong:**

1. **`android:allowBackup`.** One agent said set it `false`; another said keep it `true`. **Resolved:
   keep `true`.** `false` also kills device-to-device transfer, which is a legitimate,
   non-cloud restore path and the only one Android offers. The exclusion must be expressed in
   `data_extraction_rules.xml`, not by the blunt flag. **Two follow-ons that are not optional:** the
   rules must be *deny-all* rather than an exclusion list, because an exclusion list is an
   allowlist-by-omission that every directory added later escapes silently (`restore/`,
   `snapshots/`, `export/failed/` were all uncovered); and the rules file must be written **once**,
   in one section, rather than independently in §2.9 and §6.6.1 — which is how the design ended up
   with two different sets naming two different recovery-wrap paths. Gate G-7 asserts the shape and
   the path constant, not a substring.
2. **Keychain accessibility, a three-way split** — `AfterFirstUnlockThisDeviceOnly` vs
   `WhenUnlockedThisDeviceOnly` vs `AfterFirstUnlock`. **Resolved:
   `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, for every item the app stores, not just the
   DEK.** `WhenUnlocked*` breaks the background drain; dropping `ThisDeviceOnly` puts the item in
   iCloud Keychain, which violates constraint #1. `expo-secure-store` defaults to `WHEN_UNLOCKED`
   **[V]**, so this must be passed explicitly on every call, and gate G-10 iterates D119's
   enumeration rather than reading one item back.
3. **Device-protected spool vs "do not build the direct-boot spool".** These are two questions and
   the earlier answer to the first one was wrong. **Resolved: the spool lives in
   credential-protected `context.getFilesDir()/spool/`.** DE placement buys nothing — it does not
   widen the capture window (the same `MATCH_DIRECT_BOOT_AUTO` default gates every *sender*, so no
   bank app can post pre-unlock **[V]**) and it does not widen the drain window (the unsealing key
   is DEK-derived, hence CE-gated) — while downgrading the protection class on the most sensitive
   bytes in the app and putting them in backup domain `device_file`, where a `domain="file"`
   exclusion silently fails to match. Building a `directBootAware` listener with a CE/DE split
   remains rejected, and **the manifest must not declare `android:directBootAware="true"` on the
   listener**, or the closed decision silently reopens.
4. **What the recovery wrap actually is.** Three sections specified three incompatible answers —
   D4/D5 (AES-256-GCM under Argon2id over a 160-bit code), §2.7.1/§2.7.2 (PBKDF2-HMAC-SHA512 at
   210k + AES-GCM over a 32-character Crockford base32 code, in a native `MMKeyStore`), and §6.1
   (Argon2id + XChaCha20-Poly1305 over a 15-word BIP39 phrase) — plus two paths
   (`recovery/dek.wrap` and `keys/recovery.wrap`) and two metadata carriers (an in-database
   `_backup_meta` table and a plaintext manifest). **Resolved: §6.1 is normative** (D4), the file is
   self-describing (D4a), the path is one exported constant (D9a), and `_backup_meta` is struck as
   unimplementable — restore must read the KDF salt *before* it can decrypt anything. This was not a
   documentation nit: onboarding forces one verified backup, so both files would have existed, both
   would have claimed to be the recovery artifact, and the two flows would have asked the user for
   two different secrets.

#### 7.1.5 What the divergence actually costs the data layer

Three places where the shared schema stops being platform-neutral, all of which must be visible in
the UI rather than papered over:

1. **`confirm_state` has a lower ceiling on iOS.** `reconciled` requires an authoritative
   cross-check — a matched statement line or a continuous balance chain. Android gets both routinely;
   iOS gets neither without statement import. The honest iOS default ceiling is `confirmed`, and §3.5
   already says so. **Consequence: PDF/CSV statement import is a first-class iOS feature, not a
   settings-screen afterthought** — it is the only path to `reconciled` and the only source of an
   authoritative balance.
2. **The balance-chain oracle is Android-mostly.** `balance_breaks` is the only mechanism in the whole
   design that can detect a capture that *never arrived*, and it needs bank messages carrying a
   running balance. On iOS it is close to inert, which also means `kind = 'inferred_gap'` transactions
   will be rare-to-absent there.
3. **Conservation invariant I5 has almost nothing to conserve on iOS.** The sweep check compares
   `bank_auth` observation counts against transaction counts per account-day; with no passive capture
   there are no `bank_auth` observations, so the guard against a scoring regression eating a purchase
   simply does not fire. The under-merge bias in §3.12 is therefore doing more work on iOS than on
   Android, and auto-merge should stay off there longer.
4. **The hold-expiry timer means something different on each platform, and the default follows.**
   `clearing_state = 'expired'` (D53) is a correctness mechanism against phantom holds *when the
   absence of a settlement message is informative*. On Android with a `balance_trusted` sender it
   is. On iOS it is not: settlement is never observed by construction, so the timer is firing on no
   information at all and removing a real transaction from every budget and balance. **Therefore
   the default on iOS-without-statement-import, and on any sender with no observed `bank_settle`
   role, is "ask", not "expire".** Wherever it does fire, the transition sets `needs_review = 1` and
   `v_review_inbox` carries an explicit `clearing_state = 'expired'` branch — leaving the §3.5.2
   reporting predicate is a user-visible event, never a silent one.
5. **`clearing_state` defaulting to `'unknown'` is an iOS-total outage, not an edge case.** `'unknown'`
   is not in the §3.5.2 predicate, and §4.2.1's transition table only ever left it via a bank
   message. iOS has no bank messages, so without D55's insert-time derivation *every* iOS
   transaction shows in the timeline and contributes zero to every total — a full timeline against a
   €0 spend figure. Sweep **I15** is the standing guard.

### 7.2 Risk register

Ranked by blast radius. Tier 1 is the tier that justifies this section existing: there is no cloud
copy, so several of these have no recovery at all.

#### Tier 1 — unrecoverable data loss

| # | Risk | Why it bites here | Mitigation, and where it lives |
| --- | --- | --- | --- |
| R1 | DEK exists only in Keystore/Keychain → lost, stolen, wiped or bricked phone is **total** loss of the user's financial history, and Android→iOS migration is impossible by construction **[V]** | The user who diligently exports backups is *still* wiped out, because the export is ciphertext under a key that never left the dead device — they believed they were protected | Recovery-code wrap is generated **during onboarding**, with forced re-entry verification and one proven backup **before** real data is entered. No "skip for now" that survives the first ten transactions. Full restore tested on a factory-reset device before v1 |
| R2 | The 67-character raw-key format **fails open, not closed**: a 66- or 68-character or non-hex string silently becomes a PBKDF2 passphrase, producing a *different* DEK **[V]** | No error is raised. Every affected user's database is permanently unopenable, with nothing to fall back on | Regex `/^x'[0-9a-f]{64}'$/` at the single construction site; startup create→close→reopen self-test reading a sentinel row; unit test on length. Gates G-1, B3 |
| R3 | Default `android:allowBackup` ships the database to Google Drive — a constraint-#1 violation with **no build error and no runtime symptom** **[V]**. The exclusion-list form of the fix has the same property: `restore/`, `snapshots/pre_NNNN.db` and `export/failed/` were all uncovered, and `snapshots/` is a full `sqlcipher_export` **under the live DEK** present on disk during every update window **[NEW]** | Simultaneously a policy breach and useless: the ciphertext restores onto a phone whose Keystore lacks the wrapping key. Worse in the exclusion-list form — the wrapped DEK and the ciphertext land in the *same* Drive account, which is a complete offline-attackable package (infeasible against the 15-word phrase; a routine GPU crack against the opt-in user-chosen passphrase, whose Argon2 salt and parameters the manifest publishes) | **Deny-all `<cloud-backup>`** (D9): a root `<exclude>` per domain, so a future directory cannot leak by omission. One rules file, owned by one section. `dataExtractionRules` + `fullBackupContent` land in the same commit that creates the manifest. Gate G-7 asserts the deny-all *shape* plus a runtime test enumerating every directory the app creates |
| R4 | Backup is stale or was never taken, while the app's framing implied it was automatic. **Second form: the backups exist and are all at a superseded `recovery_code_generation`** **[NEW]** | Manufacturing false confidence about the sole copy of a financial history is strictly worse than offering no backup. "Last off-device backup: 3 days ago" after a phrase rotation is true and meaningless | Loud, non-dismissable "Last off-device backup: N days ago" indicator, **generation-aware** (D101), with a count of retained backups at older generations; opportunistic attempt on foreground; **never** promise background scheduling (§7.1.2). Rotation is two-phase and cannot complete without a verified backup under the new phrase (D120) |
| R5 | Restore is silently incomplete because the export carried the `.db` but not the media directory **[I]**. **Second form: it carried both but not the undrained spool** **[NEW]** | Images live on the filesystem, not in the DB. A restore that "worked" and lost every receipt looks fine until the user opens one. Spool records written but not drained are in no backup and no restore path, and §2.8.3 asserts "Nothing is lost" — true only while the device survives | The backup artifact is a container; its manifest carries per-table row counts, media file count and sha256; restore verifies the manifest before swapping in. Gate G-17. ### 7.3 Build-time verification gates

These are the checks that must exist in CI or as a startup self-test **before** the code they guard is
trusted. Each is written to be mechanically checkable, not aspirational — and, since the recurring
defect in this design is a gate that asserts a *mention* where the finding needs an *equality*, each
is written so that it **fails today** against the design as it stood before this revision. A gate that
would already pass is not the gate the risk asked for. Ids are allocated once (next free: **G-39**).

**Encryption and keys**

- **G-1** Assert `key.length === 67 && /^x'[0-9a-f]{64}'$/.test(key)` at the single construction site,
  as a unit test *and* a runtime precondition. Startup self-test creates a throwaway DB with the key,
  closes it, reopens it and reads a sentinel row. One debug build with SQLCipher logging enabled to
  confirm the log line `using raw key only` appears rather than the PBKDF2 branch.
- **G-10** Iterate **D119's enumerated secret inventory** — not one item — and for each, read it back
  with `SecItemCopyMatching` + `kSecReturnAttributes` and assert
  `kSecAttrAccessible == kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` **and**
  `kSecAttrSynchronizable == false`. The test enumerates from the same constant list the writers use,
  so a new secret cannot be added without appearing here. Companion lint: fail on any
  `SecureStore.setItemAsync` call site with no explicit `keychainAccessible` option.
- **G-11** Android mirror of G-10: for **every** Keystore key the app creates, read it back via
  `KeyFactory` → `KeyInfo` and assert `isUserAuthenticationRequired() == false` and
  unlocked-device-required is false.
- **G-27** Grep the whole tree and assert the recovery-wrap path string appears in **exactly one**
  constant declaration and nowhere else as a literal (D9a). Assert no source file contains both
  `recovery/dek.wrap` and `keys/recovery.wrap`.
- **G-30** (R28c) Unit test: the scrubber redacts a key-bearing string (`/x'[0-9a-fA-F]{64}'/`) at both
  the logger and the crash reporter's `beforeSend`. Grep `src/capture/`, `src/extraction/` and
  `src/repository/` for `console.log` and un-allowlisted logger calls, and fail the build on a hit.

**Schema conformance** (all parse the checked-in migration `.sql` files)

- **G-2** Fail the build if any schema or migration file contains `mode: 'bigint'`, or declares a
  `REAL` column whose name matches `_minor$|_amount|_limit|_rate_(num|den)$`.
- **G-3** Every column matching `_minor$|_rate_(num|den)$|_amount$` — **not just `*_minor`** — carries a
  `CHECK (… BETWEEN -9007199254740991 AND 9007199254740991)` or the `1 AND 9007199254740991` /
  `0 AND 9007199254740991` variant. The widened pattern is what catches
  `transactions.reporting_rate_num/den` and `entries.settle_rate_num/den`, which were bare `INTEGER`
  and `> 0` respectively while `fx_rates` carried the bound.
- **G-4** Every `CREATE TABLE` ends `STRICT` or `STRICT, WITHOUT ROWID`.
- **G-5** No migration after 0001 contains `GENERATED ALWAYS AS … STORED` — rule 7 freezes the two
  that exist, and `ALTER TABLE ADD COLUMN` cannot add another.
- **G-6** Migration 0001's first statement is `PRAGMA auto_vacuum = INCREMENTAL;` and
  `journal_mode = WAL` appears after it. Irreversible after the first `CREATE TABLE`.
- **G-21** Grep for `clearing_state IN (` and assert exactly one occurrence outside the migrations and
  views — the reporting predicate is defined once (§3.5.2) or it is defined wrong somewhere.
- **G-24** Assert every `raw_captures.source_channel` enum value has a defined mapping into
  `transactions.input_channel`, in code, with a test. See **N7**.
- **G-31** (R28b) Schema lint: fail the build on any **new** closed `CHECK … IN (…)` list on an
  append-only or diagnostic table. Assert the six known lists are either open or contain every value
  D71, D131 and the D113 registry require — including `'spool_full'`, `'spool_key_lost'`,
  `'mirror_unavailable'`, `'android_notification_sms'`, `'diagnostics'` and `I10`…`I19`.
- **G-35** Assert `integrity_findings.check_id`'s permitted set is exactly the D113 registry, and that
  every `I`-number referenced anywhere in the codebase appears in it — the guard against three
  sections each inventing `I12`.
- **G-33** (R13b) Grep for a `value_source_rank` computation and assert exactly one definition site,
  inside the §5.2.2 chokepoint module.

**Platform configuration**

- **G-7** After `:app:processReleaseManifest`, assert the merged manifest references
  `android:dataExtractionRules` and `android:fullBackupContent`. Then, on `data_extraction_rules.xml`:
  (a) assert `<cloud-backup>` has the **deny-all shape** — a root `<exclude path=".">` for every
  domain including the `device_*` variants — rather than enumerating expected excludes, because an
  enumeration cannot catch a directory added later; (b) assert the `<device-transfer>` include path
  strings are **exactly equal** to the exported path constants for the database, media, keys and
  capture-mirror directories, and that the `<cloud-backup>` exclude set is a superset of everything
  the app can create; (c) assert the listener component does **not** carry
  `android:directBootAware="true"` (conflict 3, §7.1.4). Companion runtime test: enumerate every
  directory the app creates during a scripted session and fail if any is not covered.
- **G-8** After first open, assert `isExcludedFromBackup == true` on the **directories**
  `db/`, `media/`, `keys/`, `export/`, `snapshots/` and `restore/` — not on the `.db` file, since
  `-wal`/`-shm` are created afterwards and a per-file flag misses them.
- **G-9** Resolve the DB path and assert it does **not** begin with
  `containerURL(forSecurityApplicationGroupIdentifier:)`. This is the structural guard behind R24.
- **G-23** Assert `targetSdk = 36`.
- **G-25** (R27b) Instrumented: post 200 notifications through a bound listener, and separately drive
  an `onListenerConnected` with 150 active notifications, asserting no main-thread block exceeds a
  frame budget. Folded into B3's device session.
- **G-34** (R27c) Instrumented: mutate `capture_senders`, tear down the JS runtime, post a synthetic
  notification, and assert the producer's admit/reject decision matches the table. Repeat with the
  mirror file deleted and assert (i) the notification is rejected and (ii) a `nomirror` marker exists
  that the next drain turns into a `capture_gaps` row.
- **G-29** (R6a) Runtime assertion, exercised by a test that forces `SQLITE_FULL` mid-export: after
  every backup, migration and restore procedure — success **or** failure — `PRAGMA foreign_keys`
  reads back `1` on the live connection, and `PRAGMA foreign_key_check` on the **live** database
  returns no rows.

**Money and time correctness**

- **G-12** `convert()` against a checked-in golden-vector file covering MGA, MRU, JPY, KWD, CHF, ISK
  and all seven exponent-3 currencies. Run it twice and assert **bit-identical** output — re-derivation
  after a rate correction must not emit spurious diffs.
- **G-13** Property test: largest-remainder split parts always sum to the original exactly, for random
  totals and part counts.
- **G-14** Property test: generate random multi-currency transactions through **every** mutation path
  and assert per-currency `SUM(amount_minor) = 0`, `SUM(account_amount_minor) = 0` per account
  currency, `SUM(entries.reporting_amount_minor) = transactions.reporting_amount_minor`, and that
  every non-`draft` transaction has a `transaction_seals` row (sweep checks I1, I2, I16 and I19 must
  be empty).
- **G-36** Split a transaction across three categories, then drive a settlement arrival and a
  money-bearing edit through §4.9, and assert the split survives: leg count, per-leg `account_id`, and
  every `line_items.entry_id` still non-NULL. Sweep **I12** must be empty. This is the executable form
  of R13c and it fails against `ON DELETE SET NULL`.
- **G-37** Net worth: seed a foreign-currency account, advance the rate, and assert
  `v_net_worth_asof(D, base)` revalues at D's rate rather than summing historical
  `reporting_amount_minor`, with the difference landing in `sys_unrealized_fx` (D123).

**Pipeline correctness**

- **G-15** Ingest the same synthetic bank push twice from two `node_id`s → exactly one `raw_captures`
  row with `seen_count = 2`. Ingest two identical coffees three minutes apart → two rows and two
  transactions. **Third assertion:** a child notification plus its `InboxStyle` group summary carrying
  the same amount produce **exactly one** transaction; and the same `getKey()` re-posted with changed
  text supersedes rather than creating a second. All in the same test file, because they pull in
  opposite directions.
- **G-18** Repository test that fails on any `UPDATE` touching more columns than were marked dirty.
- **G-19** An OTP-shaped SMS from a non-allowlisted sender produces a `raw_captures` row with
  `payload_text IS NULL` and `process_state = 'ignored'`. **Run the same assertion over the
  `android_notification_sms` relay channel**, where the posting package is allowlisted but the bank
  shortcode is not — the arm that the original `android_sms`-only test could never fail. **Third arm:**
  enable diagnostics for a sender, ingest an OTP-shaped message, let `diagnostics_until` lapse, then

- **G-20** Purge a capture and assert `corrections.training_eligible = 0` for every correction on it

- **G-22** Every generated `bank_templates.regex` passes a nested-quantifier detector and survives an

- **G-32** (R13a) Correct a merchant and a date on the confirm sheet, then run a replay of the same

- **G-38** Consent ordering: spool N captures under `retain_for_training`, revoke, then drain. Assert

**Backup and restore**

- **G-16** Restore a v3 backup into a v7 build and a v7 backup into a v3 build. Assert forward

#### 7.4.1 Class A — closed. Do not re-open, do not spike.

#### 7.4.2 Class B — blocking gates. A spike must run before the code it gates is written.

Ordered by what they block, not by interest. **B0, B1, B2 and B3 all run before migration 0002 is
written** — they are the "run migration 0001 on a real device" batch. They are not parallel: **B0
comes first, because B1 cannot run against a binary that does not build.** **B11 joins that batch**:
it gates the `allowBackup="true"` position, which decides the shape of `data_extraction_rules.xml`

#### 7.4.3 Class C — product calls, not research

No spike settles these. Each has a recommended default so they do not block.

| # | Call | Recommendation |
| --- | --- | --- |
| C1 | Do `authorized` transactions count toward budgets? | **Yes** (as §3.5.2 has it) — users want the coffee to appear immediately. Two consequences must be accepted explicitly: the `expired` timer and the `hold_ttl_days` defaults become load-bearing for report correctness, so the expiry sweep ships in v1; and **expiry must be a visible event, not a silent one** (R16a) — it sets `needs_review`, it has its own review-inbox branch, and on any platform or sender where settlement is never observed the default is *ask* rather than a timer, because there the absence of a settlement message carries no information |
| C2 | iOS backup posture | **Exclude from all backups.** `NSURLIsExcludedFromBackupKey` is believed to exclude from iCloud **and** local Finder/iTunes backups alike — there is no per-file "local only" control **[I, verify against the File System Programming Guide before locking this]**. | C3 | Retention defaults | Bank notification/SMS raw text 30 days; **receipt images kept until confirmed plus a grace window, then oldest-first eviction above a user-set cap (default 1 GB) — the "180 days" alternative is withdrawn**, because a flat TTL deletes the original of a receipt whose capture is still unextracted, which is D104's defect in its other form; voice audio deleted immediately after transcription (7 days if training opt-in); OCR text follows the image; confirmed transactions forever.
