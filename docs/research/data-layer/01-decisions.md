## Decisions

The data layer is **one encrypted SQLite file plus a sibling media directory**, both in the app's
own container and never in a shared one, with four strata stacked on top of each other that are
never allowed to bleed together. The **capture stratum** (`raw_captures`, `media_assets`,
`observations`) is an immutable record of what physically arrived on the device. The **provenance
stratum** (`extraction_runs`, `extracted_fields`, `corrections`, `transaction_fields`) records what
a model said, how authoritative the evidence was, and what the user changed — which is both the
audit trail and the FunctionGemma-270M training corpus. The **event stratum**
(`transaction_events`, `fx_rates`, `oplog`) is append-only and is the authoritative history. The
**projection stratum** (`transactions`, `entries`, `budget_periods`, the views) exists only because
a phone cannot fold an event log at render time; it is a real double-entry ledger balanced per
currency, hidden behind a flat façade that neither the LLM nor the UI ever sees through.

Decisions are numbered flat (D1…D131) across all groups so later sections can reference them
stably. **Numbers are allocated once and never reused**; a superseded decision is rewritten in
place, never renumbered. Group headings are prose only. Every row that resolves a disagreement
between the six research agents names the losing option and why it lost.

Three cross-cutting allocation registries live here because they are the things that silently
collide when several sections are written in parallel. **Decision ids** are D1…D131 (next free:
D132). **Build-time gate ids** are G-1…G-38 in §7.3 (next free: G-39). **Startup-sweep check ids**
are I1…I19 — see D113 for the full allocation table; nothing may invent an `I`-number outside it.

### A. Engine, encryption and key management

| ID | Decision | Why — and what lost |
| --- | --- | --- |
| D1 | `@op-engineering/op-sqlite` 17.1.3 with `"op-sqlite": { "sqlcipher": true }` is the only SQLite binding. | Bundles SQLite 3.51.3 and a SQLCipher amalgamation at the same version, and calls `sqlite3_key_v2()` inside `open()` before any statement, so the "key must be first" ordering hazard is already handled. *Lost:* expo-sqlite (SQLCipher vendored at 3.49.1, and it makes you issue `PRAGMA key` yourself, reintroducing both the ordering bug and the SQL-injection shape); WatermelonDB (no release since 2025-04, sync-engine-shaped, no encryption story); SQLite3MC (technically nicer ChaCha20-Poly1305 AEAD, but no RN binding ships it and adding it means forking a native build). |
| D2 | The DEK is passed as the exact 67-character string `x'<64 lowercase hex>'`. | This is SQLCipher raw-key mode: it skips 256,000 PBKDF2-HMAC-SHA512 iterations entirely and turns cold open from hundreds of milliseconds into a memcpy. The length test is `pass_sz == raw_key_sz + 3`; off by one and SQLCipher silently PBKDF2s the literal string instead, producing a permanently unopenable database with no cloud copy to fall back on. |
| D3 | One choke point constructs the key, asserts `/^x'[0-9a-f]{64}'$/`, and a startup self-test creates, closes, reopens and reads a sentinel row from a throwaway DB. | The 67-char format fails **open**, not closed — there is no error, only a different key. This is the single highest-consequence bug the design can ship. |
| D4 | Envelope encryption: a random 32-byte DEK, wrapped twice — (A) AES-GCM under a platform Keystore/Keychain key for silent launch, (B) XChaCha20-Poly1305 under an Argon2id KEK derived from an app-generated **15-word BIP39 recovery phrase** (160 bits + checksum). **§6.1 is the single normative specification of the recovery secret, the KDF, the AEAD and the wrap file; D4/D5 and §2.7.1/§2.7.2/§2.7.5 reference it and must not restate it.** The wrap file lives at exactly one path, `<appdir>/keys/recovery.wrap`, exported as one constant from the key-store module. | Wrap B is **mandatory, not optional**: Android Keystore keys are non-extractable and iOS `…ThisDeviceOnly` items never migrate, so a Keystore-only DEK means a diligent user with a backup file still loses everything on phone loss. The three-way divergence this row now closes was real and unrecoverable-by-construction: D4/D5 said AES-256-GCM + Argon2id over a 160-bit code; §2.7.1 said PBKDF2-HMAC-SHA512 at 210k + AES-GCM over a 32-char Crockford base32 code in a native `MMKeyStore`; §6.1 said Argon2id + XChaCha20 over a 15-word phrase — *different secret, different KDF, different AEAD, and two different paths* (`recovery/dek.wrap` vs `keys/recovery.wrap`). Two engineers building from two sections would ship two files, and a user who wrote down 15 words could not enter a base32 code. *Lost:* the base32 code (BIP39 round-trips through a password manager and self-checksums) and PBKDF2 (it was only ever justified by "no extra dependency", and libsodium is in the tree regardless). |
| D4a | `recovery.wrap` is a **self-describing, versioned binary blob**: `[magic "MMWRAP"][version:u8][kdf_id:u8][m_kib:u32][t:u32][p:u32][salt:16][nonce:24][AEAD(DEK)][tag]`. Nothing outside the file may be needed to unwrap it. `meta.recovery_salt_hex` and the `.mmbak` manifest's `kdf` block are redundant convenience copies, never the source of truth. | Both paths that actually need Wrap B have neither the database nor a manifest. §2.7.5's Keystore-invalidation flow runs *because the database will not open*, so a salt in `meta` is inside the file it is trying to unlock; an Android `<device-transfer>` restore has no `.mmbak` at all. Storing the salt anywhere but inside the wrap means either a hardcoded fallback salt (silently a shared-salt scheme) or a correct phrase that cannot open anything. `kdf_id` is what lets the KDF change later without orphaning older wraps. Gate G-16 unwraps a `recovery.wrap` with an empty `meta` table and no manifest present. |
| D5 | Crypto dependencies: `react-native-libsodium` 1.7.0 for `randombytes_buf`, `crypto_generichash` and `crypto_aead_xchacha20poly1305_ietf_*`; `react-native-argon2` 4.0.0 for Argon2id; `react-native-quick-crypto` 1.1.6 only if a platform AES-GCM primitive is needed outside the native key store. | libsodium does not expose `crypto_pwhash`/Argon2id on native (sumo/web only), which is exactly why Argon2 is a **separate** dependency rather than a reason to drop libsodium — the earlier "No libsodium" phrasing was a non-sequitur and contradicted §6.1, which uses three libsodium primitives. If Argon2id ANRs on the floor Android device (spike B8), the answer is to lower `m` and record a new `kdf_id`, **not** to switch primitive in one section and not the other. |
| D6 | Every Keychain/Keystore item the app creates is `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` with `kSecAttrSynchronizable = false` (Android: `setUserAuthenticationRequired(false)`, `setUnlockedDeviceRequired(false)`); the DB, its `-wal`/`-shm` siblings and the media directory stay at the container default `NSFileProtectionCompleteUntilFirstUserAuthentication`. The item list is enumerated once (D119) and gate G-10 iterates it. | The drain path and `BGContinuedProcessingTask` must open the DB with the screen locked, and a `WhenUnlocked` key would be strictly tighter than the files it protects. The reason this row now says *every* item rather than "the DEK": the class was specified, argued and CI-asserted for `mm.dek.v1` alone while at least three other secrets existed with no class named, and `expo-secure-store`'s default is `WHEN_UNLOCKED` — which is not `ThisDeviceOnly`, so `backup_kek` written with no options is eligible for iCloud Keychain and for an encrypted Finder backup. That is the one secret whose entire purpose is to be independent of the device, leaving the device. *Lost:* Agent 2's `WHEN_UNLOCKED_THIS_DEVICE_ONLY`; raising the DB to `NSFileProtectionComplete`. |
| D7 | Android: the DEK-wrapping Keystore key uses `setUserAuthenticationRequired(false)` **and** `setUnlockedDeviceRequired(false)`. | Bank alerts arrive at 3am with the screen locked. `setUnlockedDeviceRequired(true)` is the only thing that would manufacture the "locked device cannot write" problem; both flags default to false, and credential-encrypted storage stays unlocked from first unlock until reboot, so the ordinary screen-locked write already works. |
| D8 | `expo-secure-store` for key storage, behind a two-method interface. Do not introduce `androidx.security:security-crypto`. | react-native-keychain has not published since 10.0.0 (2025-03-23); EncryptedSharedPreferences was deprecated in April 2025 over StrictMode violations and OEM keyset-corruption crashes. A single wrapped 32-byte DEK needs neither — a Keystore AES/GCM key plus ciphertext+IV in ordinary SharedPreferences is sufficient and has no deprecated dependency. |
| D9 | Keep `android:allowBackup="true"`, and ship `dataExtractionRules` (API 31+) in which **`<cloud-backup>` is deny-all by construction** — an `<exclude>` at the root of every domain (`file`, `database`, `sharedpref`, `external`, `root`, and the `device_*` variants) — while `<device-transfer>` is include-only with exactly three entries: `database .`, `file media/`, `file keys/` (plus `file capture/` for the D126 mirror). A matching `fullBackupContent` for API ≤30. | `allowBackup="false"` also kills device-to-device transfer, which is a genuinely useful and constraint-compliant restore path (direct D2D, never a Google server). *Lost:* Agent 1's `allowBackup="false"`. Two defects force the deny-all shape. (1) The rules were written twice, differently: §2.9 excluded `database`/`media`/`spool`/`mm_keys.xml` and **included `recovery/dek.wrap`**, while §6.6.1 excluded a longer set and included `keys/`. Neither excluded `restore/`; §2.9's version shipped the wrapped DEK *and* `snapshots/pre_NNNN.db` (a full `sqlcipher_export` under the live DEK, present on disk during every update window) to Google Drive. Wrapped-key plus ciphertext in one Drive account is a complete offline-attackable package. (2) An exclusion list is an allowlist-by-omission: every directory added later leaks by default, with no build error and no runtime symptom. Deny-all inverts that. |
| D9a | **Every path that appears in a backup rule is exactly one exported string constant** — the recovery wrap (key-store module), the database directory, the media root, and the `capture/` mirror directory (D127). The rules XML, the restore path, the backup container writer, the producer and gate G-7 all reference those constants; no path is ever written as a literal twice. G-7 asserts *string equality* between each `<device-transfer>` include and its constant, not that the file "mentions `keys/`". | An Android `<include>` whose path matches nothing produces no error, no warning and no log line. The design had the code writing `keys/recovery.wrap` and one rules file including `recovery/dek.wrap`; a D2D transfer would then move the database and the media and not the one artifact that can open them, and the user would type a correct phrase at a new phone holding their entire history and be told it cannot be read. A gate that greps for a substring cannot catch that; a gate that compares the constant can. |
| D10 | iOS mirror: `NSURLIsExcludedFromBackupKey = true` on the `.db`, `-wal`, `-shm` and the media directory. A CI check greps the merged Android manifest for `allowBackup="true"` without the extraction rules. | op-sqlite's iOS default path is `Library/`, which Apple backs up; only `Caches/` and `tmp/` are excluded by default. iCloud Backup is public cloud, and its keychain copy is encrypted under a Secure Enclave UID key that restores only to the same physical device. |
| D11 | Receipt images are **not** separately encrypted under the DEK on device; they rely on Android FBE and iOS Data Protection. The backup artifact encrypts them, because it leaves the device. | App-level image encryption costs CPU on every thumbnail render and complicates export, and buys protection only against an attacker who has already defeated platform disk encryption. This is a deliberate call, not a default. |
| D12 | `cipher_plaintext_header_size` is never set; there is no plaintext header and no separately-persisted salt. | It exists primarily for WAL databases in an iOS shared container, and D46 removes that need entirely by keeping the DB out of the App Group. |
| D13 | `performanceMode` stays off. | It compiles with `SQLITE_THREADSAFE=2` while `open()` still passes `SQLITE_OPEN_FULLMUTEX`, which that build ignores — mixing op-sqlite's sync and async APIs on one connection then becomes unsynchronised access. The workload does not need it. |
| D14 | Drizzle ORM pinned to **exactly** 0.45.2 (`drizzle-orm/op-sqlite`), with every migration a checked-in SQL file. All DB access sits behind a thin adapter (`open/close/exec/transaction/prepare`). | Drizzle ships first-party op-sqlite and expo-sqlite drivers and a migrator; Kysely has no op-sqlite dialect and no migration generator, and its plugin layer cannot fix int64 because the truncation happens in C++ below JS. 1.0.0 has been in RC since ~May 2026 and its relational-query API changed. The adapter exists because op-sqlite is a one-maintainer project bundling its own SQLite, SQLCipher and OpenSSL. |
| D15 | Migration 0001 opens with pragmas in a fixed order: `auto_vacuum = INCREMENTAL` (statement one, before any DDL), `journal_mode = WAL`, `synchronous = FULL`, `foreign_keys = ON`, `journal_size_limit`, `busy_timeout`, `temp_store`. | `auto_vacuum` is irreversible after the first `CREATE TABLE`; changing it later means a full `VACUUM` of an encrypted multi-hundred-MB file on a phone. `synchronous = FULL` over the usual WAL `NORMAL`: NORMAL survives an app crash but not power loss, and there is no upstream copy. *Lost:* Agent 1's `NORMAL`. `foreign_keys` and `busy_timeout` are per-connection and must be re-issued on every open. |
| **D119** | **One enumerated secret inventory.** A single table in §2.7.4 (mirrored in §6.1) lists every Keychain/Keystore item the app creates — the Wrap-A DEK wrapper, `backup_kek`, the WebDAV credential, and any future item — each with its accessibility class, `kSecAttrSynchronizable = false`, and its Android `KeyGenParameterSpec` flags. Gate G-10 iterates the enumeration; a lint fails any `SecureStore.setItemAsync` call without an explicit `keychainAccessible` option. Note there is deliberately **no** separate spool secret in the list — D57 derives it from the DEK. | The accessibility rule was specified, argued and CI-asserted for exactly one item while three others existed with no class named. Two concrete failures follow from the `WHEN_UNLOCKED` default: `backup_kek` becomes iCloud-Keychain-eligible (the key to every `.mmbak` under the current phrase generation, leaving the device), and the WebDAV credential read fails with `errSecInteractionNotAllowed` (−25308) during the §6.4 foreground attempt whenever the app was foregrounded from a notification tap with the screen locked — so the staleness banner climbs while the app reports "no reachable destination", which is precisely the false-confidence state R4 exists to prevent. |
| **D120** | **"I forgot my phrase" and "my phrase was seen" are two different flows.** *Regenerate* (hygiene / forgotten) stays a 32-byte rewrap. *Compromised* mints a **new DEK**, `sqlcipher_export`s the live database into a new file keyed with it, swaps atomically, deletes the old file plus every `snapshots/` and `export/staging` artifact, purges the cached `backup_kek`, and marks every prior `backup_runs` row superseded. Either flow is **two-phase**: generate → verify re-entry → perform and verify (A1–A9) at least one backup under the new phrase to a destination the user picks → *only then* rewrite `keys/recovery.wrap` and bump `meta.recovery_code_generation`. Until that backup is delivered, the previous generation's wrap stays on disk under a generation-suffixed name. | Rewrap-not-rekey was presented as an unqualified benefit. It is one for the forgotten case and it is the *removal of the only remediation* for the exposed case: every prior `.mmbak` contains a `recovery.wrap` that the old phrase still opens, and it still yields the **unchanged DEK**, which still opens the live database and every later copy of it. The two-phase rule fixes the other half: rotation as specified orphaned every existing backup the instant it completed, did not trigger a new one, and left `meta.backup_staleness_days` (7) to decide when one might be attempted — so a user who rotated because the phrase was exposed, destroyed the old phrase as instructed, and was robbed two days later had a folder of files and no way to open any of them. The completion screen states plainly that pre-rotation `.mmbak` files remain decryptable with the old phrase and should be destroyed. |
| **D121** | **A logging and crash-reporting policy is part of the storage design, not an afterthought.** Structured logger with a field allowlist (ids, enum states, counts, durations) and an explicit denylist (`payload_text`, `payload_meta_json`, `raw_output`, `merchant_raw`, any `*_amount_minor`, `rate_text`, media paths, any `x'…'` string). A mandatory scrubber runs at both the logger and the crash reporter's `beforeSend`, keyed on `/x'[0-9a-fA-F]{64}'/` among others; `sendDefaultPii: false`; DB and network breadcrumbs disabled. Every `ATTACH … KEY "x'…'"` call site is wrapped so the raw statement can never reach an error path — catch, replace the key span, rethrow. Gate G-30. | The key is interpolated into SQL **by design** (§2.11.2, §6.2.3), justified on injection grounds, which says nothing about disclosure. `assertRawKey()` carries a `// NEVER log k` comment; nothing else does. A Drizzle query logger left on, or one repository `catch (e) { log.error('sql failed', { sql, e }) }`, ships the literal `ATTACH DATABASE '…' AS bk KEY "x'a3f1…'"` to the self-hosted GlitchTip instance, indexed and searchable next to the install id. On the backup path that leaks one `.mmbak` key; on §6.8.2 step 5 the snapshot is keyed with **the DEK itself**. |
| **D122** | **`PRAGMA foreign_keys = OFF` is only ever entered through a `try/finally` that re-issues `= ON` on every exit path, and each of the three procedures that use it runs `PRAGMA foreign_key_check` on the **live** database afterwards, not only on the copy.** The backup export additionally runs on a **dedicated second connection** so the live connection's FK state is never touched at all. The repository reads back `PRAGMA foreign_keys` before every write batch and refuses to proceed at `0` — **that assertion belongs to the repository's write connection only, never to the export connection, which is FK-off by design and would otherwise refuse to run the job the rule exists to protect.** | The pragma is correctly issued outside any transaction (it is a no-op inside one) in §6.2.3 step 0b, §6.8.2 step 2 and §6.5 step 6 — and each restores it only on the success path, on the single long-lived write connection every subsequent write in the process uses. One `SQLITE_FULL` during a backup export therefore leaves the whole process running with every `ON DELETE RESTRICT` in §3 inert, and D50 calls those restrictions "the undo and restore mechanism". Archiving one old credit card then succeeds and orphans thousands of `entries`; `foreign_key_check` next runs at the *next* launch. |

### B. Representation — money, identity, time

| ID | Decision | Why — and what lost |
| --- | --- | --- |
| D16 | Money is a signed `INTEGER` count of minor units with `CHECK (col BETWEEN -9007199254740991 AND 9007199254740991)` on every money column — and the same bound on **every integer column read back as a number**, which explicitly includes `transactions.reporting_rate_num`/`reporting_rate_den` and `entries.settle_rate_num`/`settle_rate_den` (`CHECK (… IS NULL OR … BETWEEN 1 AND 9007199254740991)`). Gate G-3's pattern widens from `*_minor` alone to also cover `_amount$`, `_rate_num$` and `_rate_den$` (see §7.3 for the literal regex). | op-sqlite reads every `SQLITE_INTEGER` through `sqlite3_column_double()` — hardcoded in C++, not configurable — so it truncates silently above 2^53, and it throws on a BigInt bind parameter. The CHECK converts silent corruption into a loud constraint failure. The rate columns were the hole: `fx_rates.rate_num/den` carry the bound, their denormalized copies on `transactions` and `entries` did not, and a composed cross rate (D31 multiplies rationals with no intermediate rounding — two ten-significant-figure sources give a denominator near 1e20) inserts silently and reads back truncated. §3.3.4 then re-derives from the truncated values, gets a different `reporting_amount_minor`, and writes an `fx_rederivations` row for a transaction whose rate never changed — the user sees "12 transactions changed by €0.34" for a correction that touched none of them, and rule 9's bit-identical re-derivation is violated with no error. *Lost:* a tighter ±9e14 operational bound; `REAL` in any form. |
| D17 | There are **no** big-integer columns anywhere, and a schema lint fails the build on `mode: 'bigint'`. | Drizzle has no `integer({mode:'bigint'})` for SQLite — the widely-cited feature never shipped. `blob({mode:'bigint'})` type-checks, silently becomes a BLOB with no numeric ordering, and throws `Buffer is not defined` in Hermes on insert. 2^53−1 minor units is ~$90 trillion, so money never needs 64 bits; only integer surrogate keys would, and D18 removes those. |
| D18 | Primary keys are `TEXT` UUIDv7. | Time-ordered so B-tree inserts stay sequential, globally unique offline so a future self-hosted sync target needs no id remapping, readable in logs. *Lost:* ULID (equivalent, less canonical); `BLOB(16)` (20 bytes smaller, but a `Uint8Array` in JS and unreadable in every log line); a content-addressed `source_hash` as the row id (kills time-ordering and complicates merge/unmerge — content addressing is expressed as a UNIQUE index on `dedupe_key` instead, which gives the same idempotency with none of the cost). |
| D19 | Hashes are lowercase hex `TEXT`, not `BLOB`. | A BLOB round-trips through op-sqlite as an `ArrayBuffer`, which is hostile in JS and unreadable in logs; 32 extra bytes per row is nothing at these counts. *Lost:* `BLOB(32)` as proposed by two agents. |
| D20 | Every money column travels as a triple: `(*_amount_minor, *_currency_code, *_currency_exponent)`, with the exponent denormalized onto the row and asserted against `currencies.iso_exponent` by insert **and** update triggers. The rule is enforced **uniformly**, not on three tables: `transaction_links` gains `currency_exponent` and `currency_code NOT NULL WHEN amount_minor IS NOT NULL`; `transactions.authorized_amount_minor`/`settled_amount_minor`/`tip_minor` gain their own bank-currency pair (D54); exponent-coherence triggers exist for `budgets`, `installment_plans` and `observations` as well as `transactions`/`entries`/`line_items`; sweep check I4 covers all six. | Storing only code + amount makes the meaning of every historical row a function of a mutable lookup table: correct one wrong exponent and a decade of history silently changes value, with no diff and no error. Enforcing it on three tables and declaring it a global rule is worse than not having the rule, because readers trust it. A JPY budget written with `currency_exponent = 2` renders ¥50,000 as ¥50,000.00 and reports 99% unused all month, and no trigger and no sweep check fires; a KWD `installment_plans` row at exponent 2 is off by 10× on every scheduled payment. |
| D21 | All tables are `STRICT`. | SQLite's loose type affinity is otherwise a live route for a TEXT to land in an INTEGER money column. |
| D22 | Timestamps are `INTEGER` unix epoch **milliseconds** UTC. Local calendar dates are separate `TEXT 'YYYY-MM-DD'` columns, **stored, not computed**, with a `GLOB` CHECK on each. | SQLite has no IANA timezone arithmetic, so the alternative is recomputing in JS on every query — and recomputation after a tzdata update would silently move historical rows between months. The GLOB CHECK is not decoration: `substr(NULL,1,7)` is NULL, which would drop rows from every month-grouped report. |
| D23 | Time is four distinct concepts: `captured_at_utc` (immutable ingestion instant, never used for reporting), `booked_at_utc` + `booked_tz` + `booked_precision`, `booked_local_date` (the grouping key for every budget and report), and `posted_at_utc`/`posted_local_date` (bank settlement, reconciliation only). | UTC alone fails in both directions for the travelling user who is the reason multi-currency exists: an 08:00 Tokyo breakfast is 23:00 UTC yesterday, a 20:00 Honolulu dinner is 06:00 UTC tomorrow. Local date alone cannot order two transactions across a timezone change. |
| D24 | `booked_month` is a `STORED` generated column on both `transactions` and `entries`, and both are **frozen at v1**. | A stored column is indexable where a `strftime()` expression is not. `ALTER TABLE ADD COLUMN` cannot add a STORED generated column, so any future derived column is `VIRTUAL` or app-maintained; a table rebuild is permitted only under the snapshot-and-rollback procedure (D101) and is never routine. |
| D25 | All intermediate arithmetic is JS `BigInt`; only the rounded result touches a column. Rounding is ROUND_HALF_EVEN in exactly one function; splits use largest-remainder allocation. | `amount × rate_num` reaches 1e20 and must never pass through `Number`. Half-up biases totals upward over thousands of rows; mixing modes makes FX re-derivation non-reproducible, which matters because re-derivation must be **bit-identical** or the correction job emits spurious diffs on unchanged rows. Largest-remainder is what makes 100.00 split three ways sum back to exactly 100.00. |
| D26 | At the TypeScript boundary money is a `Money = { minor: bigint; currency: string; exponent: number }` value type; combining two currencies without an explicit `convert()` carrying a rate id is a type error. A lint rule bans `number` for any field named `*_amount`, `*_minor` or `*_total`. | The representation invariant has to be enforced above SQL too, or the first careless `a + b` reintroduces it. |
| D27 | Crypto is out of scope for v1 via `CHECK (iso_exponent BETWEEN 0 AND 8)`, with a named migration path. | 1 ETH = 10^18 wei; int64 max holds ~9.2 ETH at native precision and the JS-safe range holds 0.009 ETH — native-precision ERC-20 balances are arithmetically impossible here and no care changes that. Exponent 8 still works: the entire 21M BTC supply in satoshis is 2.1e15. The migration path when it is needed is GnuCash's — add `amount_num`/`amount_den` arbitrary-precision decimal strings alongside `amount_minor` and move arithmetic to BigInt rationals. |

### C. Currencies and foreign exchange

| ID | Decision | Why — and what lost |
| --- | --- | --- |
| D28 | The `currencies` table is **generated at build time** by parsing the SIX Group ISO 4217 `list-one.xml` and cross-referencing Unicode CLDR `currencyData`, bundled as a seed migration, stamped with `source_version` (`iso4217:2026-01-01+cldr:47`). Never fetched at runtime. | A runtime fetch is a network dependency for something that changes a few times a year, and a fetch failure would leave the app unable to parse money at all. Generating rather than transcribing also catches the class the summaries get wrong: exponent 3 is **seven** currencies (BHD, IQD, JOD, KWD, LYD, OMR, TND), not three, and a codebase assuming /100 makes silent 1000x errors on all of them. |
| D29 | Two exponents per currency: `iso_exponent` governs storage and all arithmetic and is copied onto every money row; `display_exponent` is consumed by the formatter only. | MGA and MRU subdivide by 5, which ISO's base-10 exponent field structurally cannot express, so ISO assigns 2 and an ISO-faithful store can represent amounts that do not exist. Storing at `iso_exponent` keeps import/export interchange-faithful with no rounding; displaying at 0 matches reality. A golden-file test over MGA, MRU, JPY, KWD, CHF and ISK covers parse → store → convert → format. |
| D30 | `currencies` carries `status`, `retired_on`, `successor_code` and `redenomination_factor` (an exact decimal string) from v1. | ISO churn is live and recent — ANG→XCG (2025-03-31), ZWL→ZWG, BGN→EUR (2026-01-01). Without those four columns each of those is a data migration. |
| D31 | FX rates are stored as **exact rationals** (`rate_num`/`rate_den` INTEGER) plus `rate_text`, the source's published string verbatim. | A fixed scale has a ceiling: weak-currency pairs reach 1e6+ and 1e6 × 1e10 overruns 2^53. Rationals are exact and unbounded in the ranges that matter; `rate_text` allows auditing and diffing against a re-fetch. Cross rates multiply rationals with **no intermediate rounding** — round exactly once, at the end. |
| D32 | `fx_rates` is append-only. A corrected rate is a **new row** with `revision = prev + 1` and `supersedes_id`; a trigger blocks `UPDATE`. | An UPDATE silently changes every historical total that used that rate, with no record that it happened. |
| D33 | Rate lookup is `rate_date <= :booked_local_date ORDER BY rate_date DESC, source_priority DESC, revision DESC, id DESC LIMIT 1` — a **total** order — and the date actually used is stored in `reporting_rate_date`. A gap-fallback rate is not final: index `ix_txn_rate_stale ON transactions(reporting_rate_date) WHERE reporting_source='derived' AND reporting_locked=0 AND deleted_at IS NULL` backs a stated backfill query selecting `reporting_rate_date < booked_local_date`, which runs through the §3.3.4 audited path under `reason = 'rate_backfilled'`. | ECB/Frankfurter publish business days only, so the gap fallback is the **normal** path, not an exception — which is precisely why it must be *upgraded* when the real fixing publishes. As written the only re-derivation trigger was a revised rate, so a Saturday purchase converted with Friday's rate kept Friday's rate forever, with no query and no index to find it. The ordering was also not total: `revision` is per-`(base,quote,date,source)` under `ux_fx_rates`, so a hand-entered `manual` rate and a `frankfurter` rate for the same date both at `revision = 1` tie, and `LIMIT 1` returns whichever the index traversal reaches — a different amount after an index rebuild or a restore, which violates rule 9's bit-identical requirement. `source_priority` is a new `fx_rates` column; `manual` outranks any feed. |
| D34 | Every foreign transaction carries **two** conversions, in two different places: the **settlement** conversion on `entries` (`account_amount_minor`, `settle_rate_num/den`, the bank's rate including its spread — immutable ground truth) and the **reporting** conversion on `transactions` (`reporting_*`, derived by the app, re-derivable). **`account_amount_minor` is not write-only:** it is summed by `v_account_balances` grouped by `(account_id, account_currency_code, account_exponent)`, it carries a second seal predicate `SUM(account_amount_minor) = 0 per account_currency_code`, sweep check I16 asserts it, and a trigger enforces `entries.account_currency_code = accounts.currency_code`. | A Tokyo purchase on a USD card by a EUR-reporting user has three currencies, not two. Collapsing them loses the ability to re-derive after a rate revision without destroying the number the bank actually charged. But the account-currency dimension as originally written appeared **nowhere outside its own DDL** — no view read it, the seal did not sum it, no sweep check touched it — while `v_account_balances` summed `amount_minor` grouped by the *leg* currency. So the ¥5,000 lunch showed the USD card with a balance line of "−¥5,000" and a USD balance of $0.00 against a bank statement saying −$33.42, and `account_amount_minor = -1` would have sat there forever with I1 reporting the ledger clean. §3 must also resolve whether expense/income category accounts are single-currency (then the leg-currency `GROUP BY` in `v_category_month` is wrong) or multi-currency (then `CHECK (currency_code IS NOT NULL OR is_system = 1)` must relax for them) — the two cannot both stand. |
| **D124** | **`entries` carry the reporting conversion too.** `reporting_amount_minor`, `reporting_currency_code`, `reporting_exponent`, `reporting_rate_num/den` and `reporting_rate_date` are added to `entries`, written by **one** allocation function that converts the header total once and distributes it across legs by largest remainder, so `SUM(entries.reporting_amount_minor) = transactions.reporting_amount_minor` **exactly**. The seal trigger asserts that equality; §3.3.4 updates the leg columns in the same run; `budget_periods.actual_minor`'s source query is stated explicitly in §3.15 and `budget_periods.rate_basis` records which conversion produced it. **Leg-currency re-scaling (D50a) and reporting re-allocation are one operation over one leg set, never two passes:** any path that changes `effective_amount_minor` resolves the surviving leg set first, then re-scales `amount_minor` and re-allocates `reporting_amount_minor` against that same set inside the same unseal→write→re-seal, so the two can never disagree about which legs exist. I19 is a drift *detector* for paths that got it wrong, not the mechanism that keeps them right. | Every category rollup, budget actual and account roll-up is computed over `entries`, and `reporting_amount_minor` existed only on the header — so a conversion from many leg currencies into one budget currency provably happened with no stored amount, no rate id, no rate date and no re-derivability. Worked: ¥1,000 split 334/333/333 converts, per leg, to 167/166/166 = 499, against a header of 500. The category report and the transaction list disagree by a drifting cent per multi-leg foreign receipt and rule 9's "the parts sum to the original exactly" cannot hold, because there was nowhere to store an allocated part. It also makes re-derivation coherent: today §3.3.4 updates only the header, so anything recomputed from legs diverges permanently. |
| **D125** | **Every conversion is taken over `effective_amount_minor`, never `amount_minor`,** and `reporting_amount_minor` + `reporting_rate_*` join the dirty-column set of the settlement UPDATE in §4.9. `CHECK (reporting_source <> 'same_currency' OR reporting_amount_minor = effective_amount_minor)`; a trigger enforces `reporting_source = 'actual' ⇒ reporting_currency_code = the account's currency`. | `effective_amount_minor` is a STORED generated column and updates itself when settlement lands; `reporting_amount_minor` is a plain column and did not. A €25.00 authorization settling at €27.50 with a tip leaves the base-currency report €2.50 short forever on every tipped transaction — and `trg_budget_stale_on_reporting_change` does not even fire, because `reporting_amount_minor` did not change. Worse in the cross-currency case: `reporting_source='derived'` with an unchanged `reporting_rate_id` means the §3.3.4 job would *reconfirm* the wrong number on its next pass. `'actual'` ("the number the bank actually charged") is only coherent when the card is denominated in the base currency; nothing enforced that. |
| D35 | All ten values of the reporting/original tuple are stored, including the redundant converted amount. `reporting_source IN ('actual','manual')` and `reporting_locked = 1` rows are **never** recomputed. | Rounding is not invertible (1,250 JPY at 0.00618 → 7.72 EUR divides back to 1,249 JPY); rate direction is ambiguous without the pair; the receipt says ¥1,250 and €7.72 appears nowhere in the physical world; and `converted` is not always `round(original × rate)` — when it came from a statement it is authoritative and includes a spread. The discrepancy between stored and recomputed is itself signal. |
| D36 | FX re-derivation is an ordered, audited job: insert the new rate, select the affected transactions **through the `transaction_rate_uses(txn_id, rate_id, leg_index)` junction table** (indexed on `rate_id`), update only dirty columns on both the header and the legs (D124), write one `fx_rederivations` row per change, let `trg_budget_stale_on_reporting_change` invalidate the affected `budget_periods`. Base-currency change reuses the same path with `reason = 'base_currency_changed'`; a gap-fallback upgrade uses `reason = 'rate_backfilled'`. | The user must be able to see *"12 transactions changed by €0.34 because the 2026-07-14 EUR/JPY rate was revised."* The junction table replaces the single `transactions.reporting_rate_id` FK, which could not express a **cross rate**: D31 composes two rationals, `CHECK (reporting_source <> 'derived' OR reporting_rate_id IS NOT NULL)` forces exactly one id, and §3.3.4 selects `WHERE reporting_rate_id = :old_rate_id`. For any user whose base currency is not the rate source's base — i.e. every non-EUR user of an ECB feed — that is *all* FX transactions: the composed number is re-derivable from `reporting_rate_num/den` but not **attributable**, so a revision to one leg of the cross silently misses every row that used it, `fx_rederivations` records nothing, and the budget trigger never fires. `fx_rederivations.old_rate_id`/`new_rate_id` become nullable and are accompanied by the leg index. If §3.3.2 instead chooses to materialise composed cross rates as real `fx_rates` rows with their own id and `supersedes_id` lineage, reduction to lowest terms before insert is a **correctness** requirement (D16's bound), not an optimisation — but the junction table is still needed, because a materialised cross row must still be invalidated when either input is revised. |

### D. Ledger shape

| ID | Decision | Why — and what lost |
| --- | --- | --- |
| D37 | Real double entry: a `transactions` header plus `entries` postings, hidden behind a flat façade. The model still emits flat JSON; a pure `buildEntries(draft) → Entry[]` expands it; neither the model nor the UI ever sees the ledger. | Four everyday cases are unrepresentable in a flat transaction+category table without a hack that leaks into every report forever: a cross-currency transfer between the user's own accounts, "I paid 100 and Alice owes me 60", a credit-card bill payment (double-counts spending in every flat model), and a partial refund against a split purchase. *Lost:* the flat table. The cost objection does not survive contact with the design, because the LLM boundary is unchanged. |
| D38 | The balance invariant is `SUM(amount_minor) = 0` **per currency per transaction**, never in a base currency. Two companion predicates in the same seal: `SUM(account_amount_minor) = 0` per `account_currency_code` (D34), and `SUM(entries.reporting_amount_minor) = transactions.reporting_amount_minor` (D124). | Converting each leg independently produces rounding residuals, so a base-currency sum is off by a minor unit or two on a large fraction of cross-currency transactions and the constraint could never hold exactly. *Lost:* Agent 5's `posting` table with `home_amount_minor` and a `SUM = 0` trigger. The two companions are not the same thing: the account-currency sum is an exact identity because it is what the bank moved, and the reporting sum is exact because D124 allocates rather than converting each leg. |
| D38a | **`entries.fee_minor` is deleted.** A fee is a real leg with `role = 'fee'` against a seeded `Expenses:Bank fees` account, so the seal covers it and "what did FX actually cost me" is a category query. | `fee_minor` sat outside every invariant: the seal summed only `amount_minor`, so did `v_account_balances` and `v_category_month`. A ¥5,000 Tokyo purchase on a USD card with a $1.00 cross-border fee moved $34.42 out of the account and put $1.00 into no balance, no category, no budget and no spend total — money vanishing silently from the sole system of record. And because `role` already had a `'fee'` value, the schema offered two mutually exclusive representations of one fact with no rule saying which is authoritative and nothing stopping both from being written. If §3.7 keeps `fee_minor` as a denormalized reporting convenience instead, it needs `CHECK (fee_minor = 0 OR role = 'fee')` plus a sweep asserting the per-transaction sum matches the `role='fee'` legs — strictly more machinery than deleting it. |
| D39 | Enforcement is a **seal table**: `writeTransaction()` inserts one `transaction_seals` row as the last statement before COMMIT, and `trg_transaction_seal_verify` runs the `GROUP BY … HAVING` check. Three companion triggers make insert/update/delete on `entries` after the seal an error. | SQLite has no deferred constraint triggers and a CHECK cannot span rows, so an `AFTER INSERT ON entries` trigger fires mid-write on the first leg and always fails. *Lost:* that trigger. Be honest about what the seal is: a seal-time check, not a constraint — a write path that never seals passes silently, which is why D103 exists. |
| D40 | Every guard trigger uses `RAISE(ROLLBACK)`, never `RAISE(ABORT)`. | ABORT rolls back only the current statement and leaves the enclosing transaction open, so a repository that swallowed the error would commit a half-written ledger. Callers must treat `SQLITE_CONSTRAINT` from a guard as "already rolled back" and not attempt COMMIT. |
| D41 | `categories` is a **1:1 extension of an expense/income account**, so `entries.account_id` is a single NOT NULL FK and there is no `category_id` on `entries`. | The invariant becomes one query over one column. *Lost:* a nullable `account_id` XOR `category_id` (you cannot sum across a column that is sometimes NULL and sometimes means something else); one `sys_expense` control account with a category dimension (one concept in two columns, and someone eventually tags the checking leg). Budgets become "budget on a category's account subtree", a tree query rather than a special case. |
| D42 | **Seven** system accounts with fixed non-UUID ids: `sys_opening_balance`, `sys_fx_conversion`, `sys_imbalance`, `sys_cash`, `sys_unmatched_transfer`, `sys_unaccounted_cash`, and `sys_unrealized_fx` (equity). Opening balances are real balanced transactions, not a magic column. | That is exactly what makes `v_account_balances` a pure SUM with no special cases. `sys_fx_conversion` is where the *realized* FX position accumulates (legs carry `is_auto_balance = 1` so they are never rendered); `sys_imbalance` absorbs draft residuals so a draft is never unbalanced and "needs attention" is literally `entries WHERE account_id = 'sys_imbalance'`. `sys_unrealized_fx` is the seventh because D123 needs revaluation to be a balanced transaction rather than an off-ledger computation. |
| **D123** | **Balances are a stock and are revalued at the valuation date; flows stay at transaction-date rates.** §3.20 gains `v_account_balances_asof(:as_of_date)` (filtering `e.booked_local_date <= :as_of_date`, served by `ix_entries_acct_date`) and `v_net_worth_asof(:as_of_date, :currency)`, which converts each `(account, currency)` balance with the §3.3.2 rate resolved **at `:as_of_date`** — not with the transactions' own rates. The difference accrues to `sys_unrealized_fx`. | "What is my net worth in currency X as of date D" was unanswerable, in two independent ways. `v_account_balances` had no date predicate at all — it is a balance-as-of-now view. And the schema stored only *flow* conversions, so summing `reporting_amount_minor` over an account yields historical cost, not value: a $10,000 deposit at EUR/USD 1.10 reports €9,090.91 forever, against €9,523.81 at 1.05 — 4.5% understated, with €432.90 of unrealized gain living in no account, no category and no report. Converting the balance at D's rate instead gives the right number but no longer ties to the sum of the transaction list, and nothing said which was intended. Without an accrual account, an actual conversion later books the whole €432.90 as a one-day movement through `sys_fx_conversion`, so the month-over-month net-worth chart is a flat line and then a step. |
| D43 | System asset/expense accounts are seeded **in the base currency chosen at onboarding**, not at migration time. | **Schema note: §3.4.1 hardcodes `'EUR'` on `sys_cash`, `sys_unmatched_transfer` and `sys_unaccounted_cash`, which contradicts `meta.base_currency_code` being configurable and would give an MXN user EUR cash accounts — the seed must be parameterised or those three rows created at onboarding.** |
| D44 | `accounts.is_on_budget` is the one flag that keeps investment and savings movements out of spending reports. | Without it a 401k contribution or a savings sweep reads as a €500 spending spike. |
| D45 | Shared expenses use `receivable`/`payable` account subtypes, one per person, created on demand. No group-netting table in v1. | "I paid 100, Alice owes me 60" becomes −100 checking, +40 category, +60 `Asset:Receivable:Alice`: both the spend figure and the account balance stay correct. Per-person balances cover the stated requirement; group settlement with netting would need its own table and should be designed before the account subtypes freeze. |
| D46 | `line_items` carries a `line_type` enum and there is **deliberately no CHECK** that items sum to the total; reconciliation is soft via `transactions.line_items_delta_minor` and `needs_review`. `line_items_delta_minor` is defined as `total − SUM(amount_minor) over all rows except line_type IN ('subtotal','total')`, so a well-extracted receipt yields exactly **0** and the tolerance can be one minor unit plus `cash_rounding_minor`. `line_items.amount_minor` is **signed with the same sign as the transaction's category legs**, with `CHECK (line_type <> 'discount' OR amount_minor <= 0)`. | Without `line_type`, the extractor's "SUBTOTAL 42.00" gets summed as an item and doubles the receipt. With a hard sum CHECK, a large fraction of genuine receipts are rejected at 0.80 F1. But the old definition — `total − SUM(items where line_type='item')` — is non-zero for essentially every real receipt, because tax, tip, service charge, deposit and rounding all have their own `line_type` and were all excluded: €42.00 items + €8.82 IVA + €4.00 tip = €54.82 gives a delta of €12.82, 23% of the total, on a receipt with zero extraction errors. Every taxed receipt therefore landed in the review inbox, which is the app's main surface (C7) — training exactly the dismiss reflex R17 warns about — and a tolerance wide enough to swallow 23% also swallows a genuine 27.50-vs-275.00 decimal misparse, which is the failure §3.11.4 and §4.9 exist to catch. The sign convention was also never stated, so `items 50.00, discount 5.00, total 45.00` yields −500 or +500 depending on the implementer, with no reader able to tell which. `bbox_json` stores the OCR bounding box because tap-a-line-to-highlight-the-photo is the highest-leverage correction affordance in the app. |
| D47 | Transfers collapse into **one** transaction with source and destination legs. There is no `WHERE kind <> 'transfer'` anywhere in the codebase. **Person-to-person rails — BIZUM, ZELLE, PIX, SPEI to a non-own account, and anything the lexicon calls generic "P2P" — are removed from the auto-collapse lexicon**: they produce a *suggestion*, and the lexicon may only fire automatically when a counterparty match against one of the user's own accounts succeeds. Unresolved `sys_unmatched_transfer` legs get a `v_review_inbox` branch (with a partial index beside `ix_entries_imbalance`) and an aging rule that reclassifies them to an expense after N days. | Net worth is a SUM over asset/liability accounts and a transfer contributes zero automatically — a report-time exclusion filter is something someone eventually forgets. ATM withdrawals auto-post the counter-leg into `sys_cash`; credit-card payments get a lower auto-collapse bar because a false negative double-counts the whole card balance as spend. The P2P carve-out is the correction: those rails overwhelmingly carry real *payments*, not movements between the user's own accounts, and one-sided-transfer handling turns each into a phantom asset. Twelve €25 Bizums for dinners understate the month's spend by €300 (`sys_unmatched_transfer.is_on_budget = 0`, no category leg) **and** overstate net worth by €300 in a clearing asset that will never resolve — ~€3,600/year, drifting in opposite directions, and the promised "visible as an open item" had no surface at all: `v_review_inbox` had no branch for it and `ix_entries_imbalance` only covers `sys_imbalance`. |
| D48 | Reversal before settlement is a **state change** on the same transaction; refund after settlement is a **separate linked transaction** (`transaction_links.kind = 'REFUND_OF'`). `transaction_links` carries the full money triple (D20), and `v_txn_net` nets **only same-currency** links (`AND l.currency_code = t.currency_code`), exposing cross-currency refunds in a second column; sweep I8 is restricted to same-currency links. | A counter-transaction for a reversal creates phantom income for money that never left the account; mutating the original for a refund silently rewrites a closed month's totals. Partial refunds are N:1 by construction, and net is derived, never stored. The currency guard is not hypothetical — §4.10 explicitly contemplates re-converting a refund at the refund date's rate. Without it, ¥5,000 refunded as €30.90 computes 5000 − 3090 = 1910 and the UI reports ¥1,910 outstanding on a fully refunded purchase; the mirror case makes I8 raise "refund exceeds original — almost always a mis-linked refund" on a perfectly correct link and sends the user hunting for a mistake that does not exist. |
| D49 | Installment plans (LATAM MSI) get their own `installment_plans` table plus `INSTALLMENT_OF` links, and monthly charges are `kind = 'installment_payment'`. **Their leg composition is fixed here:** the origin purchase books the full amount to the category and the full liability; each `installment_payment` books **liability↔liability** (deferred balance → current balance within the same card) with `is_auto_balance = 1` and **no category leg**. | One purchase generating N identical monthly charges sits exactly in the blast radius of naive dedupe and naive spend reporting. Spend is **accrual** — recognised once, in full, on the purchase date; cash flow is the schedule. The leg composition is the mechanism that makes that true and it was specified nowhere, while §3.5.2's reporting predicate has no `kind` filter and D47 boasts that none exists. So: give the monthly charges a category leg (the default shape for any card charge) and a MXN 12,000 television at 12 MSI reports MXN 24,000 of Electronics across the year, blowing the annual budget by exactly 100%; give them none and the only balanced alternatives were liability↔`sys_imbalance`, which parks all twelve in "needs attention" forever. Liability↔liability is the third option and it is the correct one: the accrual query needs no `kind` filter, and the cash-flow query is `WHERE kind='installment_payment'`. |
| D50 | Soft delete everywhere (`deleted_at`), `ON DELETE RESTRICT` on every ledger reference — **including `line_items.entry_id`, which §3.8 currently declares `ON DELETE SET NULL`** — and `CASCADE` only where the child is genuinely part of the parent. `entries` has **no** `deleted_at` — legs live and die with their soft-deleted header. | With no cloud copy, soft delete *is* the undo and restore mechanism, and a hard DELETE on a transaction with entries is unrecoverable. `line_items.entry_id` is the one place the rule was violated and it is the most damaging one available: it is what silently un-splits a receipt. `rewriteLegs()` deletes and rebuilds legs on every settlement arrival and every money-bearing edit, `SET NULL` quietly detaches all 23 line items, the rebuilt two-leg transaction still sums to zero so the seal passes and I1 is clean, and the user's €90/€30 split is gone with no `FIELD_REVISED` naming it. `RESTRICT` converts that into a caught error on the first attempt. The absence of `deleted_at` on `entries` is deliberate: a leg is not independently addressable, so there is nothing for a tombstone to mean. A future sync author must not add one. |
| D50a | **`rewriteLegs()` is a re-scaling, not a rebuild, whenever more than one category leg exists.** It preserves `account_id`, `role` and `line_items` linkage and allocates the delta by largest remainder (rule 9); a full rebuild from the flat draft is legal **only** for the single-category case. A rebuild that would drop a user-created leg raises `needs_review` and writes a `field_conflicts` row instead of proceeding, and a `category_id` write against a split transaction is rejected rather than triggering a rebuild. Sweep **I12** asserts that the non-auto-balance legs sum, in the header currency, to `effective_amount_minor`. | `buildEntries(draft) → Entry[]` is a pure function of the **flat façade**, and the flat façade has no representation for a multi-way split — so any path that rebuilds from it destroys the split by construction. The same mechanism destroys the receivable leg of D45's "I paid 100, Alice owes me 60" on the next settlement. Nothing detected it: I1 checks legs sum to zero per currency (a rebuilt two-leg transaction does), I3 checks dates, I10 checks `transaction_fields.amount` against the header, and **nothing compared the leg set to the header amount** — hence I12. |
| D51 | `meta.allow_hard_delete` is the single documented bypass for the five append-only/no-delete triggers, defaulting to `'no'`. **Sweep check I14 asserts it is `'no'` at every startup, force-resets it, and writes an `integrity_findings` row** so the occurrence is recorded rather than silently corrected; §6.8.4 Trap A must reset it **in the same transaction that re-creates the triggers**, and §6.8.3's crash-recovery table clears it on both branches. | Maintenance and migration tooling occasionally must delete; making that one auditable switch is better than five triggers that someone drops in a hurry. But it is a row in a table every write path can reach, it is a kill switch for the triggers protecting `consent_grants` — the table whose entire purpose is to make a consent claim provable — and §6.8.4 *requires* application code to set it to `'yes'` mid-procedure. A process killed between the rebuild and the reset (a case §6.8.6 explicitly exercises) on the branch where the migration had already committed leaves hard deletes permanently permitted on `transaction_events`, `fx_rates`, `oplog`, `raw_captures`, `transactions` and `consent_grants`, with nothing visibly wrong until someone needs the audit trail. |

### E. Transaction lifecycle

| ID | Decision | Why — and what lost |
| --- | --- | --- |
| D52 | Three **orthogonal** state axes: `clearing_state` (what the bank says), `confirm_state` (what we know), `disposition` (what the user did). | *Lost:* a single `status IN ('draft','unconfirmed','confirmed','void')`. Collapsing them produces a ~30-state enum where most states are illegal, and the illegal ones are the bugs. Composite legality is expressed as CHECK constraints instead. |
| D53 | `clearing_state` includes `expired`, driven by a **local timer** (`hold_ttl_days`: 3 fuel, 8 default, 31 hotel/car rental/cruise), and it is **not terminal** — `expired → settled` is legal. **The transition sets `needs_review = 1`** and `v_review_inbox` carries an explicit `clearing_state = 'expired'` branch reading *"hold expired — did this go through?"*. Where settlement is never observed by construction — iOS with no statement import, or any sender with no `bank_settle` role in its observed history — the default is **ask, not expire on a timer**. | Pending authorizations can vanish without ever posting, and without this state a $1 fuel pre-auth or a $200 hotel hold pollutes the ledger forever. But the same timer fires when the settlement message was simply *missed*, and leaving the reporting predicate is invisible: MXN 480 for a restaurant meal disappears from the dining budget and the account balance eight days later, `needs_review` stays 0, `v_review_inbox` (which unions on `confirm_state IN ('extracted','needs_review') OR needs_review = 1`) matches nothing, and the timeline reads through the same predicate so the row is simply gone. The user's budget silently gains MXN 480 of headroom for a meal they ate. On iOS §7.1.5 says the balance oracle is close to inert, so nothing ever catches it — hence the per-completeness default. **Leaving the reporting predicate is a user-visible event, never a silent one.** |
| D54 | Auth → settlement is never an overwrite: `authorized_amount_minor` and `settled_amount_minor` coexist, `effective_amount_minor` and `adjustment_minor` are generated, and an `AMOUNT_ASSERTED` event records the change. **The whole auth/settle family carries its own currency pair** — `bank_currency_code` / `bank_exponent`, with `CHECK (authorized_amount_minor IS NULL OR bank_currency_code IS NOT NULL)` — because those figures are denominated in the **card's** currency while `transactions.currency_code` describes the **receipt's**. `effective_amount_minor` must never mix the two: either the bank figures are converted on the way in, or the generated column is dropped and both pairs are exposed explicitly. | The original survives in three places — the immutable `raw_captures.payload_text`, the authorized column, and the event. Scheme tolerances bound the legitimate settle/auth ratio at roughly 1.25; beyond that it is a conflict, not a match. The currency pair is the correction: §3.5 says `currency_code` is the economic event's currency and §3.7 says the three-currency case exists, and then the header mixed two of the three in one untyped integer. ¥5,000 in Tokyo on a USD card gives `currency_code='JPY'`, `amount_minor=5000`, `authorized_amount_minor=3342` (USD) and `effective_amount_minor = 3342` — a USD figure in a JPY row, 150× off. `ix_txn_block` then indexes `(account_id, currency_code, effective_amount_minor, …)` and the §3.12 blocking query hunts around ¥3,342 for a purchase of ¥5,000, so the settlement never blocks and a duplicate is created; `adjustment_minor = 3342 − 5000` feeds the §4.9 ratio test and manufactures a `field_conflicts` row. A KWD auth at exponent 3 against a header at exponent 2 puts the dedupe band off by 1000×. |
| D55 | The reporting predicate is defined **exactly once** as a shared repository constant: `deleted_at IS NULL AND disposition = 'active' AND clearing_state IN ('authorized','settled','disputed','chargeback_lost')`. Unconfirmed and `needs_review` rows **do** count. **`clearing_state` is never left at `'unknown'` on a non-draft row:** the insert path derives it from the capture channel — `'authorized'` only for an auth-shaped bank message, `'settled'` for everything else including `manual`, `camera_receipt`, `screenshot_ocr`, `voice`, `ios_share`, `ios_shortcut`, `ios_wallet_intent` and `kind = 'opening_balance'` — §4.2.1's transition table is extended to name every one of those, and sweep **I15** flags any `clearing_state = 'unknown' AND confirm_state <> 'draft'`. | `authorized` counts because users want the coffee to appear immediately; only `draft` is excluded. But the column was `NOT NULL DEFAULT 'unknown'` and `'unknown'` is not in the predicate, while §4.2.1's transition table enumerated only bank-message and cash-receipt routes out of it. On iOS — where constraint #3 means there are no bank messages at all — *every* transaction defaults to `'unknown'`, so `ix_txn_timeline` (which filters only `deleted_at` and `disposition`) shows a full timeline against a €0 spend figure. The onboarding opening balance is the same bug in miniature: seeded with `kind='opening_balance'`, it will never receive a bank message, so `v_account_balances` returns €0.00 for the account and defeats the entire point of D42. |
| D56 | `transaction_events` is the authoritative history; `transactions` is an explicitly denormalized projection over it. | The timeline and the budget screen are the two hottest surfaces on a phone and neither can afford to fold an event log at render time — but the projection must never be the only copy of a fact. |
| **D126** | **Budget staleness is invalidated by everything that moves a row across the §3.5.2 reporting predicate, not only by amount edits.** §3.19 gains `AFTER INSERT ON transactions` and `AFTER UPDATE OF clearing_state`, `disposition`, `deleted_at` and `booked_local_date` variants (the date one invalidating both the old and the new period), all using the same `period_start <= booked_local_date AND period_end >= booked_local_date` predicate — and respecting `budgets.date_basis`, or `date_basis` is dropped. | The two existing triggers fire on `reporting_amount_minor` and on the three amount columns. Neither fires on the transitions that actually change membership of the predicate, and the `clearing_state` one is the important case because it is driven by a **sweep**, not a user write — so "the repository marks it stale on write" is not available as a defence. A $200 hotel hold authorized 2 June counts toward June's Travel budget; the 3 July expiry sweep flips it to `expired`, it leaves the predicate, no trigger fires, and June keeps reporting $200 of travel spend the transaction list no longer contains. Identical for VOID, soft delete and the losing side of a MERGE; and without the INSERT trigger a live budget only updates when some *other* row in the period is edited. D53, R16 and C1 all call this coupling load-bearing. |

### F. Capture pipeline

| ID | Decision | Why — and what lost |

| D57 | Producers (Android `NotificationListenerService`, the iOS Share Extension, the iOS App Intent) **never touch SQLite**. Each writes one sealed file to a spool directory, and the durability sequence is specified, not left to the implementer: write `<uuidv7>.part` → **`fd.sync()`** → `rename()` into `inbox/` → **`fsync()` the `inbox/` directory descriptor**. Media first, manifest last as the commit marker. The main app is the only consumer, and it **deletes the spool record immediately after the drain transaction commits** rather than moving it to `spool/processed`. | One inbox, three producers, one drain implementation, identical `capture` states on both platforms. `rename()` is atomic on APFS and ext4/f2fs — but atomicity of the *directory entry* says nothing about the file's data reaching stable storage, and f2fs (the default on most modern Android devices, including the whole B3 target mix) offers no ext4-style replace-via-rename writeback heuristic. A power loss between rename and flush leaves a correctly-named, zero-length or truncated manifest: `openSealed()` fails BLAKE3, the file is quarantined, and the capture is lost with only a counter to show for it. The fsync cost lands on the dedicated spool thread (D57a), never on the callback thread, and is accepted because the spool file is the **only** copy of a capture between arrival and drain. `spool/processed` is deleted because the `raw_captures` row is the durable copy and `ux_raw_captures_dedupe` already makes re-drain idempotent — retaining it meant every verbatim message body the app ever saw persisting on disk forever, invisible to the §5.8.3 purge (which touches only database rows) and to §5.9's verification test (which greps columns, not the filesystem). `spool/quarantine` is likewise capped by count and age rather than "retained forever". *Lost:* a shared SQLCipher handle with a second Kotlin writer; `UserDefaults(suiteName:)`. |
| D57a | **The spool sealed-box key is derived from the DEK** — `crypto_kdf_derive_from_key(DEK, "mmspool")` / `HKDF(DEK, "spool-x25519-v1")` — so the system has exactly **one** secret, and it already carries two wraps. `onNotificationPosted` reads every extra out of `Notification.extras` into an immutable Kotlin data class on the callback thread and `post()`s it to a **single dedicated `HandlerThread`** owned by the service; all hashing, sealing and file I/O happen there, serialized, so spool ordering still matches arrival order. The same handoff applies to `onListenerConnected`, whose reconciliation batch is capped. The app's own package is on the producer's reject list, ahead of the allowlist test. | The design spends §2.7.1, §6.1 and R1 arguing that a Keystore-only key is the worst failure available, then created a **second** Keystore-only secret for the capture inbox with no Wrap B — and §4.4.1's mitigation ("retained forever… the private key may be recoverable") describes no mechanism by which recovery ever occurs. An OS update that invalidates the keyset (a documented failure mode, the reason Wrap B exists) recovers the database and permanently loses a weekend of sealed notifications, which on Android have **no** retroactive backfill. Deriving from the DEK also fixes a spec bug: libsodium's `crypto_box_seal_open()` needs the raw 32-byte X25519 scalar, and an Android Keystore key is non-extractable and usable only through `KeyAgreement`, so "the private key lives in the keystore" was not implementable as written. If a record is nonetheless undecryptable, the drain writes a `capture_gaps` row with `cause = 'spool_key_lost'` bracketed by the file's mtime — it is a **gap**, not a decryptable-later quarantine. The threading half is separate and equally load-bearing: `NotificationListenerService` dispatches both callbacks on the service's **main Looper**, which is the thread React Native renders on. Two SHA-256s, a sealed box, a temp write and a rename, ×140 active notifications on an `onListenerConnected` after a memory-pressure rebind — plus a first-call `System.loadLibrary` — is a multi-second main-thread block on the 4 GB B9 target, and the button Android offers at the 5 s ANR is **force-stop**, which drops the user straight into D68's undetectable dead state. |
| D58 | Android capture is **native Kotlin in the app's single main process**. No headless JS task, no `:capture` process, no React Native notification-listener library. **Consequence, made explicit rather than rediscovered per feature: any state the producer needs that lives in SQLite reaches it only through the D127 mirror contract.** | JS is not running when a notification arrives, the extraction model is not loaded at that moment anyway, and a headless task costs hundreds of ms and tens of MB per notification. Both RN libraries last published in 2022 and 2023. op-sqlite has no native query API at all — its entire Android Kotlin surface is 157 lines exposing `install()`, `getDylibPath()` and `moveAssetsDatabase()` — so this is not a choice between bindings. The explicit consequence is added because the design then assigned SQLite-resident state to Kotlin four separate times (the `capture_senders` allowlist, `capture_health`/`capture_gaps` writes, the `bank_templates` fingerprint history behind redaction detection, and the consent snapshot), and every one of those gaps fails toward **silence** — the single failure mode a sole-system-of-record app cannot tolerate. |
| D59 | **No foreground service for capture.** | `ManagedServices.getBindFlags()` already returns `BIND_FOREGROUND_SERVICE`, so the listener process gets foreground-service oom_adj for free with no FGS type, no Play Console declaration and no Android 15 `dataSync` 6h/24h cap with ANR-on-timeout. Extraction runs in plain WorkManager instead. |
| D60 | **No direct-boot capture path**: no `directBootAware` listener, no CE/DE split, no second encrypted store. `capture_gaps.cause = 'boot_before_unlock'` is a documented, permanent product limitation. **The spool directory lives in credential-protected `context.getFilesDir()/spool/`. Do not call `createDeviceProtectedStorageContext()`** — every occurrence of it in §3.10 and §7.1.3 is struck. | The same `MATCH_DIRECT_BOOT_AUTO` default that gates your listener gates every *sender*: a bank app that is not direct-boot-aware cannot have its process started while the user is locked, so it cannot post a notification at all. This is the single largest scope reduction available. The storage-context half was originally "one free API call" and is now a correction: DE placement extends **zero** capability — it does not widen the capture window (nothing can post) and it does not widen the drain window (the unsealing key is D57a-derived from the DEK, hence CE-gated) — while downgrading the most sensitive bytes in the app from *encrypted under the user's credential* to *encrypted under a device-bound key the OS can use before anyone has authenticated*. It also breaks the backup rules silently: device-protected storage is backup domain `device_file`, not `file`, so a `<exclude domain="file" path="spool/">` matches nothing. |
| D61 | The SQLite file stays in the **app's own container** and is never reachable from a second process. An architecture test asserts the DB path never resolves under `containerURL(forSecurityApplicationGroupIdentifier:)`. | SQLCipher + WAL in an iOS App Group container is a deterministic `0xdead10cc` termination on **every** backgrounding — Signal built a reproduction repo showing it across all iOS versions and devices, and the documented mitigations are described by practitioners as "surprisingly difficult" to get right. The test exists so that a future widget or App Intents Extension cannot silently reintroduce it as a background-termination statistic weeks later. |
| D62 | The iOS Share Extension **stages bytes only**: `loadFileRepresentation` + `copyItem`, never `loadObject(ofClass: UIImage.self)`, never a resize. Downscaling happens in the main app at drain. Gemma 4 E2B at ~0.84 GB is 7x over before you count the JPEG; even decoding a portrait-mode photo blows the budget. | D63 | App Intents are defined in the **app target** with a pure-Swift `perform()` that writes a manifest into the App Group inbox and returns. The Wallet trigger is real, fires on Apple Pay NFC taps, can run without confirmation, and hands over Merchant/Amount/Card/Date — but it misses in-app and web Apple Pay, physical cards, cash and transfers, and is reported flaky on some card providers. | D65 | Background execution is never a correctness mechanism. Background GPU access is unavailable on every iPhone, so background extraction there is CPU-only — which is fine, because the design already drains on foreground where the GPU is available. The UI shows "N items waiting"; background work only makes that number smaller. |
| D66 | The staging inbox cap is **split by payload kind**: text captures (150–300 bytes; §5.8.1 computes ten years at 30/day as ~33 MB) are capped by **bytes only**, at a level no realistic user reaches; the item cap applies to **media-bearing records only**. At the cap the iOS Share Extension refuses with "N unprocessed items — open the app"; **the Android producer, which has no UI at the moment of capture, posts a high-priority local notification and opens a `capture_gaps` row with `cause = 'spool_full'`**, closed by the drain when the inbox is back under the cap. | An unbounded queue plus CPU-only background extraction is a user who shares 300 receipts and fills it faster than it drains — which is a *media* problem. | D66a | **The insert half of the drain is opportunistic, not foreground-only.** §4.4.3 already separates "write `raw_captures` rows and COMMIT" from "extract"; only the second stage is deferred. Thirty Saturday notifications, a river on Sunday, a verified Friday `.mmbak` — the design's happy path — and those thirty captures are nowhere, with nothing writing a gap row, because the user's mental model is that anything the app already caught is safe. |
| D67 | The ingest filter runs **in the producer, before anything is spooled**: sender must be on the allowlist **as published through the D127 mirror** (the producer cannot read `capture_senders`), body must match an amount pattern, and a negative OTP/2FA/promo lexicon rejects outright. That is simultaneously a privacy property and the strongest sentence in the Play SMS declaration. One exception protects against a wrong filter: for senders that *are* on the financial list but fail the amount test, the body **is** retained. Diagnostics mode is the switch that turns the whole claim off, and nothing gave those rows a shorter TTL, a distinct state, or exclusion from the container: with `retain_for_training` on for `android_sms` — plausible for exactly the user who wants better extraction from their bank — D104 sets `purge_after = NULL`, so 24 hours of login OTPs and 3-D Secure codes become **permanently** retained, ship inside every `.mmbak` (`sqlcipher_export` copies `raw_captures` unconditionally; §6.9's toggle governs only CSV/JSONL) and are pushed to the user's WebDAV endpoint on the next foreground. |
| D68 | **Foreground-time reconciliation is the primary liveness detector; the WorkManager probe is an accelerator.** On every app foreground, before render: (1) `NotificationManagerCompat.getEnabledListenerPackages()` — the authoritative, permission-free answer to `permission_revoked`, checked **first**, ahead of any probe; (2) `PackageManager.isAutoRevokeWhitelisted()`, with a deep link to `ACTION_APPLICATION_DETAILS_SETTINGS`; (3) `now` compared against the Kotlin-written heartbeat (D127) and against each sender's learned inter-arrival distribution, opening a **retroactive** `capture_gaps` row spanning the silence. All of that stands. What does not stand is making the probe the *sole* detector: OEM battery managers, App Hibernation and the user all kill by **force-stop**, which puts the package in the stopped state and cancels its scheduled jobs — so the watchdog dies with the thing it watches and never reschedules until something in the app runs again. Even when it does run, a WorkManager `Worker` is Kotlin and cannot advance `capture_health` or open a `capture_gaps` row (D58). `onListenerDisconnected()` is an orderly-unbind callback and does not fire on a process kill, so `last_disconnected_at` is null exactly when it matters. | D69 | Android 15 redaction detection is a **differential test on the app's own fingerprint history, not a label comparison**: once a sender has ≥N successfully-parsed captures, a capture whose §4.13 `skeleton` fingerprint is novel, whose `EXTRA_TEXT_LINES` and `EXTRA_SUB_TEXT` are both absent, and whose body yields no amount-pattern match sets `redaction_suspected = 1`. But label equality was a heuristic every one of whose failure modes returns **"not redacted"**: under Android 11+ package-visibility filtering it is nowhere established that a bound listener can see the packages posting to it, and `getApplicationInfo()` throwing `NameNotFoundException` yields false, not an error (`QUERY_ALL_PACKAGES` is not an escape — it is Play-restricted and budgeting is not on the permitted-use list); and it compares the *system's* localized label against a string read under the *app's* locale, so a device whose system language differs from the app language mismatches. Meanwhile the redacted captures land as `parsed` with a null amount rather than `redacted`, so they read as "the model is bad at this bank" and `learnTemplate` burns `support_count` learning a template whose body is "Sensitive notification content hidden". |

Holding the permission is what draws review. OEM guidance (MIUI autostart, Samsung "never sleeping apps", Huawei protected apps) is harm reduction; the watchdog is the real mitigation. |
| D71 | Capture gaps are **first-class data**: `capture_gaps` (window + cause) and `capture_health` (probe state, recovery attempts, permission, `probe_available`, `last_notification_seen_at`, `last_heartbeat_at`, `heartbeat_source`). | D72 | The running-balance chain is used as a correctness oracle **only** for senders with `capture_senders.balance_trusted = 1`, earned after 20 consecutive continuous observations and lost above a 20% break rate. Unexplained gaps past 48h become `kind = 'inferred_gap'` transactions in `needs_review`. **`observations` must carry the inputs the chain arithmetic needs**: a `direction TEXT NOT NULL CHECK (direction IN ('debit','credit'))` (or a signed `amount_minor`, stated as such), and `balance_currency_code` / `balance_exponent` beside `balance_after_minor` with `CHECK (balance_after_minor IS NULL OR balance_currency_code IS NOT NULL)`. Because §4.16 ships auto-merge disabled except on `dedupe_hash`, nothing ever collapses any of it: every pair lands in the review inbox forever, filling the app's declared main surface (C7) with machine-generated noise and training exactly the dismiss reflex that then swallows R8's genuine "a merge ate a purchase" finding. `FLAG_GROUP_SUMMARY`, `getGroupKey()` and `isGroup()` appeared nowhere in the design. |

| D75 | `extraction_runs` is **mandatory for every capture**, including non-LLM ones, via sentinel engines (`wallet_app_intent`, `manual`, `rule`, `template`, `ocr`). | A Wallet capture and a manual entry have no model; if the table were optional, every consumer would branch on NULL. With sentinels, confidence is set by **provenance** rather than by a model and the audit story reads correctly: "this amount came from Apple Pay, not from a 0.80-F1 extractor." `model_sha256_hex` catches a silent model swap; `backend` explains both latency and quality deltas. |
| D76 | `extracted_fields` materializes the **canonical seven** (`/merchant`, `/total`, `/currency`, `/date`, `/tax`, `/payment_method`, `/category`) plus, lazily, any deeper path a correction touches. Everything else stays in `extraction_runs.field_confidence_json`, queried with `json_extract()`. | A 20-line receipt is 80+ rows per capture; ~35k rows/year versus ~400k. What is given up is indexed range queries on per-line-item confidence, which no query that matters needs. |
| D77 | `corrections` links by the **natural key** `(run_id, field_path)` using RFC 6901 JSON Pointers, so a correction survives even when no `extracted_fields` row was ever materialized. | This is precisely what makes the pruning in D76 safe. Accepts are not stored as rows — a confirmed capture with no correction row for field X means the model was right — except one `accept_all` row carrying the final payload, because accepted-unchanged fields are as valuable a label as corrected ones. |
| D78 | `extraction_runs.fields_shown_json` records which fields were actually rendered on the confirm sheet, and `corrections.ui_surface` distinguishes confirm-sheet edits from later edits. | The correction dataset is a biased sample: users correct what is wrong **and visible**. Without `fields_shown_json` you cannot tell "accepted" from "never displayed", and the harvest silently trains the model to repeat errors nobody looked at. |
| D79 | `transaction_fields` carries **two** provenance columns — `value_source_rank` (which extractor) and `authority_rank` (how authoritative the evidence: statement 60, settlement 50, auth 40, receipt 30, user assertion 20, inference 10) — consumed by one replacement function used by merge, settlement arrival **and** replay. | One column cannot express "the model re-read a bank settlement message" versus "the model read a photographed receipt". The equal-authority branch is what makes replay safe: a newer model may fix a misparse of the same settlement message, but a receipt can never clobber a settlement amount because 30 < 50. |
| D79a | **An ordinary user correction pins.** On every write where `actor === 'user'` and the field is bank-authoritative, §5.3.2 step 6 sets `pinned_by_user = 1` **and** `pinned_at_authority = the authority rank of the value being displaced` (not the user's own 20). The replay selection predicate in §3.11.5 excludes any transaction with `pinned_by_user = 1` on **any** field, not just the four listed. | This is not "pin everything" — it is the behaviour §3.11.4 and D79 already describe and never wire up. As written, a plain confirm-sheet edit lands at authority 20, `pinRequested` is an *optional caller flag* nobody sets, `pinned_at_authority` is never written, and all five "independent locks" in §5.4 route through `pinned_by_user`. So a re-extraction of **the very message the user was correcting** — authority 40 — silently wins: the divergence test in step 5 covers only numeric bank-authoritative fields so it does not fire for a merchant or a date, the final clause `accept iff new.authority_rank > cur.authority_rank` is true, both corrections revert, `USER_VALUE_SUPERSEDED` is not written (that branch requires the pin), `needs_review` is not raised, and the shadow gate does not stop it because the per-`(sender, fingerprint)` change rate is low precisely *because* most rows were never corrected. The 7-day undo window then expires unnoticed. And the replay predicate selects any run with `overall_confidence < 0.90`, which at a 0.80-F1 operating point is the majority of the captures the user actually had to correct. With the pin set, `SUPERSEDE_PINNED` rejects the same-authority re-parse (40 > 40 is false) while still letting a settlement (50) and a statement line (60) through, loudly. |
| D79b | **`value_source_rank` has exactly one definition, and it lives at the chokepoint that computes it (§5.2.2).** The formula is the composition of both concerns, evaluated in order: `channel_precedence * 100000 + ENGINE_BASE * 100 + min(pipeline_rank, 99)`. §4.5.1 keeps its channel-precedence table as **input data** and its formula block is replaced by a reference; §5.3.2 step 2's "never accept this from the caller" already makes the chokepoint authoritative. §4.7's Scenario A arithmetic is re-derived against it. | Two sections each presented a different single formula and both fed the same equal-authority tiebreak. §4.5.1: `channel_precedence * 1000 + pipeline_rank` (user edit ≈ 10,000, SMS re-extraction ≈ 80,003). §5.2.2: `ENGINE_BASE[value_source] * 100 + min(pipeline_rank, 99)` (user edit ≈ 1,000, any LLM run ≈ 403). They give **opposite** answers for the case that matters: a truncated notification and its full relaying SMS for one purchase, where the user fixed the merchant. Under §4.5.1 the SMS beats the human at 80,003 to 10,000, so there is no configuration in which the human wins; under §5.2.2 the human wins and §4.5.1's whole purpose — "full SMS text beats a truncated notification regardless of arrival order" — silently does not happen. Both produce plausible integers, so whichever an implementer picks, the other section's worked example is quietly wrong. |
| D80 | Large disagreements become `field_conflicts` rows, not silent precedence — and the divergence test covers **non-numeric bank-authoritative fields too**: any change to `merchant_id`, `occurred_at`, `account_id` or `direction` that reverses a prior user value is a `field_conflicts` row, never a precedence question. | Receipt 27.50 versus SMS 275.00 is a decimal-separator misparse, and applying precedence quietly is how a 1000× error becomes permanent. Restricting the test to numeric fields meant the two most commonly corrected fields in the app — the merchant and the date — had no divergence path at all, so the only thing standing between a user's correction and a machine reversal was the pin that D79a now sets. |
| D81 | Replay after a model/prompt/schema bump is append-only, gated on charger + Wi-Fi + idle, chunked with a resumable watermark, shadow-diffed before applying, and undoable as a single unit for 7 days. It never overrides a user pin (D79) or a match veto (D86). | A worse model on one bank's format would otherwise regress data that was previously correct, and thousands of churned rows burn battery. Every replayed change writes a `FIELD_REVISED` event, which is what makes "undo this re-scan" a real button. |
| D82 | `bank_templates` are learned from user confirmations by aligning confirmed values back into the raw text, promoted at `support_count ≥ 3` with zero disagreements, demoted on 2 consecutive disagreements or match rate below 0.80. Promoted templates are immutable and versioned — drift produces a new fingerprint and a new candidate, never an edit. | The parser ladder degrades with nothing dropped: active template (≈0 ms, works before the model is downloaded and after the user deletes it) → LLM → `needs_review` with raw text → `deferred_no_model`. The honest failure mode that most designs omit is explicit: if a **required** field has no locatable span, the model **inferred** it rather than extracting it, so the pair is marked `llm_only` and never templated again. |
| D83 | `bank_templates.decimal_separator` and `date_format` are decided **once per template**, never re-detected per message and never inherited from the device locale. Generated regexes bound merchant groups at `{1,60}`, reject nested quantifiers, and run under a 10 ms timeout with auto-quarantine after two timeouts. | `1.234,56` parsed as 1.23 or 1234.56 is the worst silent bug the app can have. And a learned regex is code generated from model output plus user input — catastrophic backtracking would hang the ingest worker. |
| D84 | The category taxonomy is two layers: `taxonomy_keys` is a frozen, versioned closed set of ~70 leaves and is **the only output space the model ever sees**; `categories` is a user-editable tree mapping many-to-one onto it. The model emits the **key**, never the display name. | With constrained decoding (GBNF, `@Generable`, LiteRT-LM function calling) a closed set compiles to a grammar alternation that makes an invalid category structurally impossible — 100% valid output, no post-hoc string matching, no hallucination. A free-text field cannot be constrained at all; a fixed enum alone is unusable for people ("Padel court fees"); an LLM-invented free-text category is worst of all — unbounded labels, no aggregation, no budgets. Display names are localized and renameable; keys are stable tokens that survive both, and `taxonomy_version` is stamped on every run so a taxonomy change cannot poison the corpus. |
| D85 | `category_aliases` and `merchant_patterns` drive a deterministic pre-pass that short-circuits the LLM entirely for known merchants, and every confirmation inserts or increments a pattern row. | This is the single biggest latency and battery saving available, and it improves with zero model involvement. `merchants.country_code` and `default_currency_code` also feed the currency-disambiguation ladder directly: `$` at a merchant with `country_code = 'MX'` is MXN. |

### H. Deduplication and matching

| ID | Decision | Why — and what lost |
| --- | --- | --- |
| D86 | Deduplication is **two unrelated problems**, never conflated: exact delivery idempotency (`raw_captures.dedupe_key`, no fuzziness ever) and cross-channel entity resolution (runs **only** between different `source_channel` values). | Conflating them is the root cause of the classic "two coffees merged into one" bug. |
| D87 | `dedupe_key` must contain an **OS-assigned** timestamp — never the app's own receipt time, never omitted. | `getPostTime()` is preserved when a notification is re-delivered via `getActiveNotifications()` on rebind, so re-delivery is byte-identical, while two genuine coffees three minutes apart carry different postTimes. Omitting postTime merges the coffees; using `System.currentTimeMillis()` duplicates every re-delivery. On conflict the drain increments `seen_count` rather than dropping, so re-delivery storms are observable. |
| D88 | `transactions.dedupe_hash` (under the partial UNIQUE index `ux_txn_dedupe`) is `sha256(normalized_sender_or_merchant, amount_minor, currency_code, event_minute_truncated, card_last4)` — it **includes** a truncated event timestamp. | A UNIQUE constraint cannot express a time window, so a time-free hash under this index would collapse two genuine identical purchases — the exact failure the rest of §H exists to prevent. *Lost:* Agent 6's time-free `dedup_hash` matched by a ±72h query window, which is a different mechanism and incompatible with the index the schema declares. **Schema note: §3.10 and §3.12 declare `ux_txn_dedupe` but never define the hash's composition; this row defines it and should be folded back into §3.12.** |
| D89 | Five **structural** rules protect two genuinely separate identical purchases, not tolerance tuning: G5 same-channel (never fuzzy-merge two observations sharing `(source_channel, source_app, role)` — **except when `source_ref` is identical, per D128**), G6 slot capacity (enforced in the database by `ux_observations_slot`), G3 strong-identifier mismatch (auth code / RRN / ARN / folio differ ⇒ forbidden regardless of score), density escalation, and G9 conservation. | A bank emits exactly one auth message per authorization, so two messages from one bank are two purchases. Putting slot capacity in the database rather than application code is what makes it survive a future code path nobody audited. The `source_ref` escape hatch is what keeps G5 from turning an *updated* notification and a group summary into a duplicate factory — see D128 for why that premise fails on real Android. |
| D90 | **Bias to under-merge, explicitly.** v1 ships with auto-merge **disabled** except for exact strong-identifier matches; everything else becomes a review suggestion. `match_decisions` records the full score vector and the user's response so thresholds are tuned against a local on-device dataset after ~2 weeks, with `algo_version` making the comparison possible. | A duplicate is visible and one tap to fix; a wrong merge silently deletes a purchase from a database with no cloud copy — invisible, and unrecoverable in practice. The weights and the 0.88/0.55 thresholds are engineering judgement with no data behind them, and shipping them merge-happy is the one failure mode that cannot be walked back. Do not hedge in the UI either: "possible duplicate" with a merge button, never auto-collapse with an undo toast. |
| D91 | `match_vetoes` keys on **capture** identity, not transaction identity, with a canonical `a < b` ordering enforced by CHECK. Gate G7 consults it on every evaluation, including during replay. | Transaction ids change under merge and unmerge; capture ids never do. A user who says "these are two different coffees" is never asked again, and a smarter model is not allowed to overrule them. |
| D92 | Merging repoints `observations.txn_id` and writes a `MERGED` event; it never destroys history, and the loser is kept as `disposition = 'merged_into'`. Unmerge re-projects both transactions from their observation sets. | Unmerge is only possible because nothing was deleted, and the retained tombstone is also what stops a re-import from resurrecting the row. |

### I. Sync, backup, export, retention

| ID | Decision | Why — and what lost |
| --- | --- | --- |
| D93 | **No sync engine in v1.** The schema carries HLC, `node_id`, tombstones, `oplog` and dirty-column discipline from day one so sync is additive later. | All of it costs nothing today and is a painful migration later. The whole problem collapses onto one decision — where the DEK lives — and that is D4. |
| D94 | Ordering uses a hybrid logical clock (`hlc TEXT` as `<48-bit ms hex>:<16-bit counter hex>:<node_id>`), not `updated_at`. `node_id` lives in `meta`, outside any replicated table. | Device clocks are user-settable; an NTP jump, a manual clock change or a timezone move silently reorders edits under `updated_at`, and the loss is invisible. An HLC is one TEXT column, comparable with plain `<`, monotonic per device, no library. |
| D95 | Conflict resolution is **per-field**, not per-row, and the data layer writes **only dirty columns** — no full-row UPDATE, enforced by a repository test. | Extraction at 0.80 F1 makes correction the normal path: device A confirms the merchant while device B fixes the amount seconds later, and per-row LWW throws one edit away. Dirty-column writes make per-field merge free under Turso-style last-push-wins *and* under a hand-rolled merge, and are unretrofittable after a year of ORM full-row writes. *Lost:* CRDTs and cr-sqlite — nothing here is CRDT-shaped (no shared counter, no ordered list, no collaborative text), cr-sqlite is in maintenance mode, and it almost certainly cannot compile alongside op-sqlite's `sqlcipher` flag. |
| D96 | Sync candidates evaluated and rejected for v1: **ElectricSQL** (explicitly does not do write-path sync — it is the read half only); **PowerSync** (requires a central backend source database, which contradicts "the on-device DB is the sole system of record", plus four self-hosted services and an FSL-licensed service edition); **CouchDB/PouchDB** (the only one a genuine non-expert can self-host, and the RN adapter is alive — but it is a document-model fork that kills SQL reporting, FTS5 and joins); **file rsync** (not sync at all, and a WAL corruption trap). | Each loses on architecture, not on licensing or effort. CouchDB stays the named fallback if D97 stalls. |
| D97 | Self-hosted **Turso** (`tursodb --sync-server`, MIT, single binary) is the named v1.5 path, gated on four concrete conditions: local at-rest encryption exposed by the React Native binding; documented authentication for the sync server; a resolution for op-sqlite's `turso` flag **replacing** the SQLCipher backend rather than complementing it; and acceptance that its conflict handling is bare last-push-wins. | Choosing it today would mean a finance app with an unencrypted local database, and its `remoteEncryption` is server-side BYOK held in server memory — acceptable on a machine the user owns, but it is not end-to-end and must never be sold as "the server never sees my finances". | D98 | Backup is `ATTACH '…mmbak' AS bk KEY "x'<recovery-derived key>'"; SELECT sqlcipher_export('bk'); DETACH`, preceded by `PRAGMA wal_checkpoint(TRUNCATE)`, run on a **dedicated second connection** and with the FK window under `try/finally` (D122). | One statement, consistent, fully encrypted under a **different** key, no plaintext intermediate, nothing streamed through Hermes, and the result is a normal SQLCipher database the user can open in third-party tools. *Lost:* `VACUUM INTO`; a raw file copy. `sqlcipher_export` does **not** copy `user_version`, which is why D102 exists. The second connection is a correction rather than an optimisation: the export must run with `foreign_keys = OFF` (rows copy in `sqlite_master` order, so `fx_rederivations` inserts before the `transactions` it references), and doing that on the process's single long-lived write connection means one `SQLITE_FULL` leaves every `ON DELETE RESTRICT` in the schema inert for the rest of the session. §2.10.2 already contemplates a second connection and lists the per-connection pragmas it needs. |
| D99 | The backup artifact is a **container**: the `.mmbak` plus the media directory, with a **plaintext `manifest.json` written last, outside the encrypted member** (schema version, app version, node id, per-table row counts, source SHA-256, KDF salt and parameters). "Backup without images" is the default fast path; "full backup" is an explicit choice. | Because images live on the filesystem (D107), a backup that ships only the database is silently incomplete on restore — a correctness requirement, since there is no cloud copy. **The earlier `_backup_meta`-table-inside-the-attached-database proposal is struck as unimplementable, not merely duplicative:** restore must read the KDF salt *before* it can decrypt anything, so metadata living inside the encrypted member cannot serve the purpose it exists for. The manifest is plaintext **by design**, carries only versions, counts, salts, parameters and hashes — never a merchant name, an amount or a sender address — and its arrival is the container's commit marker. It is a fast-fail convenience, not the integrity authority: that is `PRAGMA quick_check` over SQLCipher's per-page HMAC, which a tampered manifest cannot fake. |
| D100 | Transport is the **OS file layer**: share sheet / `UIDocumentPickerViewController` on iOS, SAF `ACTION_CREATE_DOCUMENT` on Android, so the user drops the file into whatever Nextcloud/Syncthing/USB path they already operate. The only built-in network target is a WebDAV `PUT` with basic auth, and it is **gated by the `transmit_offdevice` consent purpose (D105), per-invocation by default**, over TLS with redirects disabled and no plaintext-HTTP fallback; the automatic variant is a separate opt-in whose consent screen names the artifact's contents. | Zero network code, works with any user-owned destination, no reachability failure mode. *Lost:* S3-compatible (SigV4 signing); SFTP (no maintained RN library). Do **not** name Dropbox in the destination list without stating the posture — an end-to-end-encrypted container in a third-party sync folder is the user's call, but constraint #1 is written as absolute and the doc should not appear to endorse public cloud. |
| D101 | There is **no promise of automatic backup**. v1 offers a user-triggered export always, an opportunistic attempt on foreground when the last successful backup is older than the threshold, and a loud, non-dismissable staleness indicator ("Last off-device backup: 12 days ago"). The staleness computation is **generation-aware**: backups at an older `recovery_code_generation` do not satisfy it, and the backup history screen shows how many retained backups are at older generations. | iOS `BGProcessingTask` can go days without firing and Android WorkManager is Doze-throttled and OEM-killed. A scheduled backup the user believes is running but isn't is strictly worse than none. The generation clause closes the D120 hole from the other side: "Last off-device backup: 3 days ago" was true and meaningless the moment a rotation completed, because every one of those files needed a phrase the user had just been told to discard. |
| D102 | Onboarding **forces** recovery-code generation with re-entry verification **and** one successful backup to a chosen destination **before** the user enters real data. Restore-on-new-device is a first-class onboarding branch, tested Android→iOS and iOS→Android on a factory-reset device. | A passphrase set once and never used is forgotten, and there is no reset. Proving the path while the stakes are zero is the only way it works when they are not. These are the two items product will want to cut and they must not be cut. |
| D103 | **Backup and export are different deliverables and must never be conflated.** Backup is opaque, complete and restorable; export is CSV/JSONL, human-readable, lossy and explicitly **not** restorable — and the UI says so. | D106 | Retention defaults, all user-adjustable in one screen: bank notification/SMS raw text 30 days; **receipt images kept until confirmed plus a grace window, then oldest-first eviction above a user-set cap (default 1 GB) — there is no flat 180-day image TTL**; voice audio deleted immediately after transcription (7 days if training opt-in); confirmed `transactions` rows kept forever. `corrections` is never pruned. | The ledger is not a capture. `corrections` is tiny and is the entire v2 dataset. | D108 | Training exports are **immutable snapshots** recorded in `training_exports` (row count, JSONL SHA-256, exact capture id list, version filter), version-gated on `schema_version` and a compatible `prompt_version` set, wrapped in an encrypted archive **using the same KDF and parameters as the backup container (D4a's `kdf_id` block), not a second invented one**, whose passphrase is never the DB key. | **D129** | **Restore is crash-safe by the same construction the migration path already uses.** `meta.restore_in_progress = '<backup_id>'` is written and COMMITted in its own transaction before extraction begins and cleared only at the end; **both wraps for the new DEK are written and fsynced before the first byte of the live database is created** (§6.5 step 7 moves ahead of step 6); and startup gains the branch: `restore_in_progress` set AND the live DB fails its key proof ⇒ delete the partial live DB and re-offer the restore, **never** the recovery-code flow. §2.7.5's `provision()` precondition becomes `!databaseFileExists() && !recoveryWrapExists()`, with a wrap-without-database state routing to "we found recovery material but no data — restore?" rather than minting a fresh DEK, and the recovery wrap is never opened for writing outside the D120 rotation flow. | Restore mints a new DEK and `sqlcipher_export`s into the live location **before** either wrap of that DEK is persisted, with no in-progress marker — while the migration path has both a marker and a three-way crash-recovery comparison. Restore is the longer, more memory-intensive, first-run-on-a-new-phone operation, i.e. exactly when iOS jetsams. 1. **"Suppress sweep check I5 for users whose device UTC offset ≠ 0" (R17a's interim mitigation).**
   *The defect is real and its permanent fix is adopted; only the interim step is rejected.*
   Suppressing I5 for every non-UTC user disables it for essentially the entire target market,
   which means the only global guard against R8 ("a wrong merge deletes a purchase invisibly") is
   off for everyone who matters, for an unbounded period, behind a config flag nobody will remember

   one-line change to a query that has not been written yet — there is no migration, no data to
   backfill and no shipped behaviour to preserve, so the trade the interim step is buying does not
   exist. R17a is amended in §7.2 accordingly: fix it before I5 ships, do not ship it disabled.
