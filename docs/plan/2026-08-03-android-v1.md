# Android-only v1 — scope and implementation plan

## 1. The decision

**v1 ships Android only. iOS is paused, not cancelled.**

This supersedes the `app-layers.md` §16.4 proposal, which kept a reduced iOS v1 on Apple Foundation Models. iOS is now out of v1 entirely.

The engine decision is unchanged where it still applies: **Gemma 4 via a LiteRT-LM native module, E4B on Android**, with E2B as the low-RAM device tier rather than the iOS tier.

---

## 2. What this deletes from v1

Each of these was real, funded work in the reviewed plan. All are now out.

| Deleted | Why it mattered |
| --- | --- |
| **The macOS build host** | Under maximal self-hosting this meant real Apple hardware, kept patched on a current Xcode, uploading multi-GB ODR packs to App Store Connect every release. It was the single largest ops item and the hardest to staff. |
| **LiteRT-LM Swift binding** | Ten weeks old, and the buildability trilemma is unresolved: #3003 checksum mismatch, #2780 does not compile under Xcode 26.6, #2815 forbids version-resolved SwiftPM pins — only v0.12.0 is self-consistent. This was **the largest single technical unknown in the programme**. |
| **Metal digit corruption (#2814)** | Attacked amount and date specifically. Gone with the platform. |
| **iOS On-Demand Resources** | Model delivery is now Play Asset Delivery only. |
| **iOS Share Extension** | The ~120 MB extension memory ceiling that `increased-memory-limit` does not raise (D62), plus the two-process-writing-one-SQLite class of data-loss risk. |
| **App Intents / Shortcuts ingestion** | iOS-only capture tier. |
| **App Store review surface** | `PrivacyInfo.xcprivacy`, required-reason APIs, Guideline 2.5.2 and 5.1.2(i), Apple encryption export compliance, the seller-name question. Play remains. |
| **Apple Foundation Models adapter** | Was the iOS contingency. Not needed. |
| **iOS-gated spikes** | V27 (Swift constrained decoding), V30 (iOS image input), V17 (iOS background inference), and the iOS half of V0. |

**What is left is one platform, one engine, one store, one build host.** That is the difference between a plan that fits 2–4 people and one that does not.

## 3. What must stay iOS-portable

iOS is paused "for now", so the cost of resuming must stay low. Three rules — all of which cost nothing today:

1. **The schema stays platform-neutral.** It already is. Keep `media_assets.rel_path` relative rather than absolute — the comment cites iOS container-UUID rewriting on restore, and that reasoning stays valid. Do not "simplify" it to an absolute path because Android tolerates one.
2. **Keep the `ExtractionEngine` adapter interface** (`app-layers.md` §3.3) even with one implementation behind it. A single-implementation interface looks like ceremony right up until the second implementation arrives, and this one is already specified.
3. **Keep the producer/spool/drain split** (D57). Three producers write sealed spool files and only the main app touches SQLite. Collapsing this to "the listener writes to the database" because Android is the only producer would have to be undone to add the Share Extension back.

Everything else may be Android-specific without penalty.

## 4. The top risk has changed

With the Swift binding gone, **the riskiest item is now V29 — Mali/Dimensity GPU death after 1–3 multi-turn generations (#2421).**

This is worse positioned than the iOS risk it replaces, for one reason: **Mali is the dominant chipset family in the LATAM target market.** The iOS risk threatened a minority platform; this one threatens the majority of the primary market.

**Fallback ladder, in order:**

1. GPU moves to an allowlist in shipped configuration (`app-layers.md` §3.5) — known-good chipsets get GPU, everything else CPU.
2. Mali-class devices run **E2B on CPU** rather than E4B. Slower and less accurate, but the CPU path is measured at 17.7 tok/s decode with a 5.3 s time-to-first-token — usable for a background extraction queue, not for interactive chat.
3. If still unacceptable, that device class falls to **OCR + deterministic bank templates + manual entry**, with a visible in-app explanation.
4. The circuit breaker (`app-layers.md` §9.3) makes this automatic in the field rather than requiring a store release.

**Written stop-loss: if V29 has no green cell on Mali by end of week 2, tier 1 is adopted immediately — no debate.** Rung 3 is a fully shippable product; `app-layers.md` §11.2 already requires the app to be complete and useful with zero model bytes, so the floor is real and not a consolation.

## 5. Build sequence

### Weeks 1–2 — prove the engine before building anything around it

No React Native, no Nitro, no repo layout, no CI. Throwaway Kotlin CLIs in `tools/spikes`.

- **V0** digit-fidelity revision matrix, Android only, CPU and GPU, RSS recorded.
- **V29** Mali/Dimensity multi-turn GPU, on phones bought this week for under $500. **This is the gate that decides the product's shape.**
- **V26** 16 KB page-size alignment on Google's prebuilts — it can block every Play upload and the remedy is a multi-day source build.
- V13 clone independence, V34 false-ready smoke, **V32a** fd/mmap of a PAD-delivered `.litertlm` via `bundletool` local-testing. **V32b** (Play-reported compressed pack sizes) needs a real internal-track upload and stays in weeks 3–4, matching the register.
- Zero-engineering, in parallel: the "why this is not spyware" memo, the Gemma licensing notice and EULA clause, repo layout (V23), and the Play listing decisions put in front of product.

### Weeks 3–4 — the thinnest vertical slice

RN screen → Nitro module → PAD model acquisition → one real receipt → one extracted amount on screen, on a physical device. This exercises every integration boundary at once, which is where the surprises live. **It must exist before month two.**

### Weeks 5–8 — the layers, in dependency order

Capture (NotificationListenerService + allowlist + health monitor + V15) → the spool/drain durability sequence (D57) → schema and migrations → normalisation and the money grammar → crop-to-content (T2 OCR union first, since T1's decline rate is unmeasured) → confirmation UI → metrics ledger and circuit breaker → erasure and reconciliation.

### Weeks 9–12 — the release surface

Play listing written to measured numbers, Data Safety form, notification-access declaration with its evidence, staged rollout, internal-track upload with real compressed pack sizes. Begin collecting field evidence for the later `READ_SMS` ask.

## 6. Gates that must close before the code they govern

From `data-layer/07-platforms-risks.md` (G-1–G-39) and `app-layers.md` §13b. The blocking ones for an Android-only v1:

- **V29** — before any GPU code path is written.
- **V26** — before the first Play upload is attempted, ideally week 1.
- **G-28** — restore crash-safety (D129), before the backup path ships.
- The **device-transfer wrap-path CI check** — before `allowBackup="true"` is relied on.
- **V15** — whether NotificationListenerService survives without a foreground service. It decides whether the Play FGS declaration and its demo video are required at all.
- The **Gemma 4 tiling experiment** (`image-preprocessing.md` §11 item 3) — before segmentation is built. It may delete that work entirely.

## 7. Deferred, deliberately

`READ_SMS` (its own release, after notification field data exists — and the LATAM coverage argument makes it more important here than the reviewed plan assumed). Self-hosted sync. Tier C self-hosted endpoint. Confidence calibration apparatus. FunctionGemma fine-tune — but **v1 still harvests the training data**, and the function-call schema is frozen now so v2 trains against something that can express the real domain. Multi-shot receipt stitching. Widgets.

**iOS**, in full, until the Swift binding stabilises. The trilemma is upstream work, not ours; the sane trigger to revisit is a LiteRT-LM release where checksum, Xcode compatibility, and SwiftPM pinning are simultaneously self-consistent.

---

## 8. Still unresolved

- **Ops load remains the programme's weak point.** Deleting the macOS host removes the worst item, but maximal self-hosting still means self-hosted CI, crash reporting, key custody without a hosted secret manager, and a physical Android device lab — on 2–4 people who also need Kotlin, C++, React Native, and eventually ML fine-tuning. Play Console remains unavoidable regardless. If this proves too heavy, the first thing to relax is self-hosted crash reporting (GlitchTip is lighter than Sentry but still an estate); the last is key custody.
- **The device matrix has to be bought, not assumed.** V29 needs real Mali and Dimensity hardware in week 1. Emulators cannot test GPU inference.
